# 040. NET3 — многопользовательский lifecycle

**Дата:** 16–17 ноября 2026. [Контракт040](../decisions/040-net3-multiplayer-lifecycle.md).

Проверки выполняются реальными TCP/TLS соединениями на loopback. Отдельные тесты используют3клиента и4стороны либо8human клиентов с разным количеством navigation workers. Каждый успешный журнал независимо воспроизводится с tick-zero фабрикой; истории оставшихся клиентов сравниваются побайтно, включая управляющие записи. Численная производительность10000объектов и физический LAN не проверялись.

Предыдущее задание доведено и повторно проверено17ноября; новые режимы лобби/зрителей/альянсов — [041](041-game-shell.md).

## Исполняемые сценарии

`dotnet run --project tests/OpenRTS.Network.Tests -- --net3`:

1. Три TLS human + AI: смена конфигурации сбрасывает Ready; старый Ready не запускает матч; управление своими объектами; чат; Pause/Resume от разных гостей; одинаковая граница паузы, отсутствие продвижения во время неё; Stop и replay. Обрезанный journal отклоняется.
2. Graceful Leave гостя: общий prefix, отдельный корректный финал ушедшего, пауза оставшихся, переключение None→AI, команды ИИ через общий pipeline и одинаковые продолжающиеся журналы. Policy не вызывается дважды на одном тике и не вызывается на клиентах.
3. Асимметричный аварийный разрыв гостя: решение принимает только хост, оставшиеся стоят на одной границе и могут продолжить. Потеря хоста завершает клиента ошибкой; автономного продвижения после ошибки нет.
4. Занятый слот и неправильный TLS pin отклоняются, хост сохраняет рабочее лобби и принимает корректного участника.
5. Некорректная control revision, chat size, player range и подмена issuer/envelope отклоняются.
6. Два разных TLS relay: RTT50/jitter20 и RTT150/jitter20/модель loss5%, D3. Модель задерживает reliable bytes до recovery, не удаляет application bytes. Требуется ненулевой recovery counter, lead≤2D+H, queue≤32, одинаковый результат и replay. Это **модель**, не kernel netem и не утверждение25Гц.
7. Восемь human-слотов, D1, конечный16тик; ввод всех сторон, одинаковые результаты и байты журналов, восемь успешных replay.
8. Участник отвечает на heartbeat, но не присылает нужный batch: fixed300мс deadline срабатывает после bootstrap D−1, хост объявляет None+Pause. Heartbeat не продлевает срок. После Stop журнал оставшегося воспроизводится.

`dotnet run --project tests/OpenRTS.Tests -- --filter='NET3 AI'` проверяет реальный SkirmishAi: takeover на завершённом тике12, последующие16тиков, issuer/tick policy, запрет повторного Plan на одном тике. Это дополняет сетевой тест простой управляемой policy.

## Реальный sandbox

`./tools/dev.sh verify-network --net3 --output=/tmp/openrts-net3-ui` запускает3независимых процесса Godot. В настоящей настройке выбираются Crossroads,4стороны, человеческие слоты1/2/3 и AI4. Все проходят Ready/Start, выдают RTS команды/production, открывают локальное меню с продолжающимися тиками, затем наблюдают одну общую паузу. Хост возобновляет и согласованно завершает матч. Все3процесса проверяют свой StarJournal.Replay.

Первый прогон: пауза на тике24, итоговый hash всех3клиентов `FC6B0440E07BFACCCC912EB81BFA09FE225403C06156A7796C126BA83726D6F5`. Конкретный hash/тик завершения зависят от момента UI Submit; критерий — одинаковый результат внутри одного прогона и точное воспроизведение записанного ввода. Двухпроцессный сценарий `verify-network` также сохранён и пройден. Прогоны headless проверяют реальные Godot controls/scene lifecycle, но не внешний вид окна.

Артефакты финальной проверки сохраняются в [040-net3](040-net3/). Полный набор сетевых проверок включает прежние NET1/NET2/WAN. Новых NuGet зависимостей нет; Gameplay wire/hash форматы не изменены. StarSession и StarJournal имеют самостоятельную версию; результаты WAN039 для DirectSession не выдаются за измерение новой звезды.

Не реализованы вход/rejoin в уже идущий матч, snapshots, host migration и игровые альянсы/поражение. Безопасный авторитетный режим остаётся последней дополнительной возможностью NET8/NET9.
