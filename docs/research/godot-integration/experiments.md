# Пилоты и критерии выбора

[Обзор](README.md). **Это предложения будущих проверок. В рамках исследования они не реализовывались и не запускались.** Числа объектов ниже задают сравнительные сценарии, а не подтверждённые возможности редактора или заявленные бюджеты.

## Минимальный полезный пилот

Одна карта, три готовых типа — пехота, техника и здание; neutral и два владельца; две стартовые точки; одна разреженная terrain/visual кисть. Возможности: разместить, переместить, дублировать, удалить, выбрать type/owner, увидеть картинку и body/footprint, отменить действие, сохранить и открыть карту, получить диагностическую ошибку по объекту и запустить тот же результат в .NET headless.

Начать с существующего набора полей M1. Каталог типов остаётся YAML. Inspector показывает эффективные HP/оружие/locomotor; изменение одного действительно поддержанного поля каталога проверяется отдельной ограниченной операцией либо внешним YAML editor с обновлением preview. Не включать произвольные overrides, visual scripting, runtime hot reload definitions и миграцию ECS.

Для варианта B авторские размещения хранятся в сцене и выпускают M1. Для сравнения A достаточно того же малого документа в plugin panel с preview. Полноценную поддержку обоих путей не разрабатывать до выбора.

| Вопрос | Проверка | Условие успеха или основание изменить выбор |
| --- | --- | --- |
| Полезен ли обычный scene workflow | Одинаковые задачи автора в A и B: группа, rename/reparent, duplication, undo, сохранение | Измерить время и ошибки; если B не даёт заметного удобства, цена Godot-specific источника может быть неоправданна |
| Независим ли запуск | Подготовить карту в Godot, передать результат штатному .NET headless без Godot API/assemblies | Одинаковые terrain, definitions, порядок размещений и ожидаемый журнал; запуск не читает `.tscn` или `.godot` |
| Надёжен ли источник | Сохранить, закрыть, открыть, переместить parent, дублировать subscene; проверить IDs и позиции | Нет потери авторских данных, случайного respawn order и лишней preview-графики |
| Не устарел ли результат | Изменить linked scene, каталог типа, кисть, версию compiler; отдельно поменять только texture | Игровые изменения требуют новой сборки; косметические не меняют gameplay identity; устаревший вход не запускается молча |
| Проверка совпадает с игрой | Пересечение тел, footprint вне карты, неверный owner/type, неподдержанный transform | Ошибка ведёт к объекту/полю; мир не публикуется, частичное размещение не становится доступным хосту |
| Удобно ли менять баланс | Поменять shared HP типа, создать один variant, отдельно попытаться задать initial HP | Автор понимает scope правки; runtime данные не записываются в shared definition; неподдержанное поле явно недоступно |
| Сохраняется ли воспроизводимость | Один собранный вход и журнал при 1/4 workers, повторной загрузке и разном render FPS | Одинаковое игровое состояние по тикам; reparent без игровых изменений не меняет результат |
| Корректен ли lifecycle | Открыть/закрыть карту, перезапустить, отключить addon, пересобрать C# | Нет оставленных потоков/мира и обращений к освобождённым Godot-объектам или leases |

## Масштаб редактора и представления

Проверить расстановки 100 / 1000 / 10000 объектов. Сравнить полные preview nodes, облегчённые markers и пакетное preview с узлами только выбранных объектов. Для terrain проверить, например, 128² / 512² / 2048² samples с несколькими visual types; последний размер — 4 Mi cells, ещё не весь допустимый бюджет и не обещание приемлемой скорости.

Измерять отдельно:

- открытие документа, чтение ресурсов и построение preview;
- idle editor frame, массовое выделение, перемещение, кисть и undo;
- сохранение, компиляцию, геометрическую валидацию и холодное создание мира;
- память authoring document, editor nodes, ECS и render buffers;
- tick, кадр, передачу буферов и диагностику во время матча;
- экспорт/запуск с чистым кэшем и повторный запуск с актуальным артефактом.

Фиксировать hardware, Godot/.NET/plugin revisions, Debug/Release, renderer и параметры карты. Одинаковые картинки или число сущностей не означают одинаковую нагрузку. При масштабе, на котором markers тормозят, рассмотреть пакетное preview, а не менять ECS симуляции без причин.

Отдельно сравнить нынешние material batches и пространственные чанки при движении камеры. Не учитывать выгрузку gameplay-сущностей как оптимизацию рендера. Численный бюджет кадра и допустимое время открытия определить по рабочей карте и оценке пользователя; сейчас основания задавать их как факт нет.

## Пилот высотного рельефа

Только после базовой расстановки: маленький склон, уступ, вода и один world-space blocker. Вариант terrain editor выбирается отдельно, Terrain3D не обязателен.

Проверить scale и квантование height/slope/depth, расхождение видимой границы с collision, путь разных locomotors, остановку и footprint на краю. Сравнить Godot preview и headless результат из сохранённых baked samples. Ошибки на неподдержанном мосте/нависании должны быть явными; такие места нельзя молча сворачивать в одну поверхность. Проверить renderer текущего проекта и выбор объектов на склоне.

Условие отказа от раннего height pipeline: расхождения geometry слишком велики либо цена поддержки отвлекает от нужного тайлового workflow. Тогда оставить height редактор визуальным или отложить до отдельного изменения модели поверхностей.

## Когда пересматривать runtime или ECS

Сравнивать отдельную альтернативу с Frent следует при воспроизводимом ограничении: например, нужен критичный native subsystem, связка текущего render bridge доминирует в профиле либо Godot-owned physics является основной механикой новой игры.

В таком исследовании стоимость включала бы перенос определений, tick ownership, command ordering, collisions, observations/fog, serialization и bindings, а не только query iteration. Демонстрация частиц или простой movement benchmark не заменит RTS-сценарий. Первые кандидаты не обязаны быть текущими GECS/Godex/Stagehand: их ограничения здесь зафиксированы, но отбора новой библиотеки не проводилось.

## Рекомендуемая последовательность после исследования

1. Сравнить A/B на минимальном editor placement; выбрать источник истины для карты и границы сохранения.
2. Закрепить независимую подготовку и diagnostics; только затем расширять карту на initial state и ограниченные variants.
3. Выбрать terrain tools по виду реальной карты: нынешние кисти, TileMapLayer или отдельный height pipeline.
4. Добавлять богатые runtime views там, где конкретному объекту нужны возможности Godot.
5. Систему миссий, навигационный backend и замену ECS исследовать отдельно при соответствующем потребителе.

Основания изменить предварительный выбор B: требование редактировать и пересобирать исходные карты без Godot; неприемлемая цена scene authoring на реальной карте; сложность стабильной идентичности и зависимостей превосходит полученное удобство. Основания перейти к более тесному D: конкретная Godot-only игра выигрывает от встроенных игровых систем настолько, что владелец проекта принимает потерю независимого исполнения этих механик.
