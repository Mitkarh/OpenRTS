# Подготовка карт и свойств в Godot

[Обзор](README.md) · [Текущие ограничения OpenRTS](current-boundary.md). Всё ниже, кроме описания API и существующего кода, — **предлагаемый workflow**, а не реализованная возможность.

## Как это могло бы выглядеть для автора

Автор открывает карту, выбирает тип `rifleman`, размещает несколько объектов, выделяет группу и задаёт владельца. У здания видны реальный footprint, выход и допустимые ориентации. У юнита — тело, дальность оружия и обзора; изображения и физические размеры показаны раздельно. Ошибка пересечения выделяет оба объекта, а неизвестный тип — конкретное поле Inspector.

Кнопка подготовки проверяет всю карту теми же правилами, что и headless. Запуск использует результат этой подготовки, а не повторно угадывает данные по сцене. Остановка матча возвращает к исходной расстановке; перемещения и урон в матче сами по себе карту не переписывают.

Возможная организация сцены: корень карты; слои рельефа; расстановки юнитов и зданий; точки старта; именованные группы/регионы; отдельная ветка света, декораций, камеры и звука. Названия и типы будущих узлов здесь не являются утверждённым API. Структура дерева удобна автору; игровые порядок, ID и правила должны задаваться явно.

## Какие механизмы Godot подходят

| Задача | Механизм | Что ещё необходимо сделать в OpenRTS-адаптере |
| --- | --- | --- |
| Поля типа, владельца и начальных параметров | C# `[Export]`, группировка и hints | Выбор из действительного каталога, проверка ссылок, единицы измерения |
| Добавление специальных типов через диалоги редактора | `[GlobalClass]` для Node/Resource | Авторские wrappers, не изменение классов Gameplay ради Godot |
| Картинка и подсказки до запуска | `[Tool]`, `Engine.IsEditorHint()` | Безопасный preview и отдельный lifecycle редактора |
| Выбор типа, показ наследования и ошибок | `EditorInspectorPlugin` | Связь поля с источником, различение исходного и вычисленного значения |
| Контуры тела, footprint, range и ручки редактирования | `EditorNode3DGizmoPlugin` | Рисование по нашим численным правилам и фильтр поддерживаемых transform |
| Палитра и кисть во viewport | `EditorPlugin` | Документ карты, выбор, рисование, сохранение и диагностика |
| Единое действие undo для кисти/группы | `EditorUndoRedoManager` | Транзакции над авторскими данными, корректная dirty-state сцены/ресурса |
| Запуск и наблюдение матча | Обычный хост; при необходимости `EditorDebuggerPlugin` | Отдельный обмен диагностическими копиями и управлением сессией |

Подтверждения: [exports](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_exports.html), [global classes](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_global_classes.html), [tool scripts](https://docs.godotengine.org/en/stable/tutorials/plugins/running_code_in_the_editor.html), [Inspector](https://docs.godotengine.org/en/stable/classes/class_editorinspectorplugin.html), [gizmos](https://docs.godotengine.org/en/stable/classes/class_editornode3dgizmoplugin.html), [undo](https://docs.godotengine.org/en/stable/classes/class_editorundoredomanager.html), [debugger](https://docs.godotengine.org/en/stable/classes/class_editordebuggerplugin.html).

`[Export]` принимает Variant-compatible значения. Обычный immutable .NET `EntityDefinition` не становится editable Resource автоматически. Для малого набора параметров разумны явные wrappers. Генерация Inspector по всей ECS/schema возможна как отдельная работа после нескольких реальных типов; она не должна выставлять refs, внутренние массивы очередей и служебные компоненты.

Первый плагин логично ориентировать на встроенный `OpenRTS.Gameplay` и его контент. Пользователь одного Core может иметь собственные компоненты, команды и кадры; такой мир не получит подходящий Inspector автоматически. Игра добавляет авторские поля и подготовку своих definitions там, где они нужны. Граница общего редактора и game-specific расширений должна появляться из этих потребителей, без единой заранее заданной схемы для любого ECS-компонента.

Godot Resources обычно разделяются между потребителями. Определение типа удобно хранить общим, но HP конкретного юнита не должно изменять общий Resource типа. Редакторская оболочка обязана отличать shared definition, локальное переопределение и runtime state. [Resources](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html).

## Выбор первичного источника

### A. Независимый документ, Godot редактирует его

Карта и каталоги остаются независимыми данными. Плагин читает документ и создаёт редакторское представление: часть объектов может иметь временные узлы, массовый terrain — пакеты. Все пользовательские действия меняют документ. Сохранение пишет его, а не сериализует случайное состояние preview-сцены.

Преимущества: обычный .NET build/headless может подготовить исходную карту; проще альтернативный редактор и внешние генераторы; существующий YAML остаётся естественным входом. Недостатки: больше собственных инструментов выбора и сохранения; часть удобств scene inheritance нужно отображать на свою модель; требуется writer, которого в нынешнем `GameMap` нет.

Важно не путать импорт с редактированием. `EditorImportPlugin` преобразует исходный файл в производный ресурс в `.godot/imported`. Его изменение не является сохранением исходного YAML. Для собственного сохраняемого формата предусмотрены `ResourceFormatLoader`/`ResourceFormatSaver`, либо плагин может управлять отдельным документом. Сохранение комментариев, порядка, наследования и удаления свойств требует отдельной политики; обычная сериализация resolved definition этого не восстановит. [Importer](https://docs.godotengine.org/en/stable/classes/class_editorimportplugin.html), [loader](https://docs.godotengine.org/en/stable/classes/class_resourceformatloader.html), [saver](https://docs.godotengine.org/en/stable/classes/class_resourceformatsaver.html).

Для YAML типов возможен первый Inspector только с просмотром эффективных характеристик и переходом к источнику. Следующий срез — редактирование небольшого объявленного набора исходных полей с явной операцией сохранения. Не следует незаметно перезаписывать весь наследуемый тип развёрнутыми значениями.

### B. Сцена/Resources — источник, независимые данные — результат

Расстановка хранится в `.tscn`, небольшие повторно используемые авторские наборы — в `.tres` либо сценах. Компилятор извлекает только объявленные игровые данные и выпускает независимый вход для Content/Gameplay. Визуальная сцена остаётся Godot-specific приложением к карте.

Преимущества: привычные selection/transform tools, экземпляры сцен и их переопределения, визуальная композиция окружения. Недостатки: для повторной сборки исходной карты нужен Godot и соответствующий plugin; требуется отслеживать все зависимости компиляции. Запуск готового артефакта без Godot обеспечивает **переносимость исполнения**, но не переносимость авторских инструментов.

Для начального пилота не обязательно менять каталоги: тип задаётся стабильным строковым ID из YAML, в сцене редактируются расстановка и владельцы. Если позже `.tres` выбирается источником определений типов, YAML для этих же типов становится только генерируемым результатом или входом одноразового импорта. Двусторонняя синхронизация двух равноправных источников создаёт конфликты; её не следует включать по умолчанию.

### Практический выбор

Начать проверку B с типами из YAML — наиболее прямой способ оценить именно удобство Godot. Одновременно проверить одну маленькую карту через A: можно ли получить приемлемое редактирование без собственных копий всех scene tools. Решение зависит от того, насколько важны пользователю Godot-prefabs и подготовка исходников без Godot. Не нужно реализовывать две полноценные системы до этого сравнения.

## Изменение характеристик: четыре разных операции

| Потребность | Предлагаемая семантика | Последствия |
| --- | --- | --- |
| «Все танки этого типа имеют 400 HP» | Изменение каталожного типа, проверка всей зависимости | Меняется gameplay fingerprint; следующий матч использует новое определение |
| «На этой карте есть усиленный танк» | Именованный variant типа в наборе карты либо ограниченное авторское override → compiled variant | Детерминированный ID/порядок definitions, валидация и fingerprint обязательны; вариации желательно переиспользовать |
| «Этот танк начинает повреждённым» | Начальное состояние размещения, например initial HP, отдельно от MaxHealth | Нужно расширить карту и инициализацию; сейчас такого поля у object нет |
| «Хочу изменить HP во время теста» | Явная отладочная команда на тик с журналом и отдельной диагностикой | Не запись из Inspector в ECS; авторский документ не меняется без отдельной операции |

Урон не должен реализовываться как `MaxHealth` override, а смена спрайта — как новая физическая сущность. Для первой версии лучше выбирать готовый тип/variant, чем разрешать произвольное изменение всех capabilities для каждого размещения. Полные overrides затрагивают оружие, производство, ссылки на actions и проверки зависимостей: это отдельный content compiler, а не несколько экспортированных полей.

Глобальную скорость не следует выдавать за уже существующий независимый атрибут каждого типа: её текущая модель включает параметры мира и locomotor. Поле Inspector должно соответствовать реальному игровому контракту. По тому же правилу секунды UI переводятся в тики одним определённым способом; типизация не заменяет проверку допустимого диапазона.

Во время запущенного матча definitions рекомендуется замораживать. Изменения боевых данных применяются после пересборки и перезапуска. Обновление текстур/preview можно исследовать отдельно. Полная горячая замена оружия, body или locomotor требует согласованной инвалидации runtime state, кэшей и реплеев; обещать её первым срезом нельзя.

## Чем редактировать terrain

| Подход | Что даёт | Соответствие текущему OpenRTS | Существенные ограничения |
| --- | --- | --- | --- |
| **Собственная кисть поверх нынешнего `TerrainLayout`** | Точные terrain/visual слои, составные элементы и quarter-turns | Максимально прямое; текущий host рисует на 3D-плоскости | Палитру, выделение, историю и большие карты придётся делать; собственный UI требует пользовательской проверки |
| **`TileMapLayer` + `TileSet`** | Готовая 2D-покраска, patterns, terrain connections, custom data | Хороший кандидат для CnC-подобных тайловых карт; клетки можно скомпилировать в независимый layout | Инструмент находится в 2D viewport; нынешнее представление в 3D, нужна проекция preview. Tile IDs/atlas coordinates не должны становиться gameplay IDs |
| **`GridMap` + `MeshLibrary`** | Готовое размещение модульных 3D-мешей, collision/nav data | Уместно для 3D-декораций и модульных уровней | Не универсальный placer сцен/юнитов. Поддерживаемая структура MeshLibrary ограничена; коллизии и navmesh требуют перевода |
| **Terrain3D либо другой terrain editor** | Скульптинг, раскраска и рендер больших высотных полей | Возможный отдельный визуальный/backend модуль | Нужны bake height/slope/depth/terrain и препятствий, проверка renderer/platform и масштаба; существующая карта ещё не принимает эти слои |

Основания: [TileMaps](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html), [TileSets](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html), [GridMaps](https://docs.godotengine.org/en/stable/tutorials/3d/using_gridmaps.html), [Terrain3D README на проверенной ревизии](https://github.com/TokisanGames/Terrain3D/blob/185145cedadc93251934aba6f60625050ef155ce/README.md).

Custom data в TileSet принадлежат типу тайла и разделяются его размещениями. Для instance-свойств нужны отдельные авторские данные. Godot terrain connections выбирают соединяющиеся изображения; это не наши правила `Traverse`, `CanStop`, `Speed`, `Cost`. Scene tiles создают отдельные экземпляры сцен, поэтому ими нельзя без измерений заменить компактную расстановку большого леса.

Terrain3D предоставляет height/control/color import-export, но control map имеет собственный формат. Нужен явный перевод texture/control IDs в игровые terrain IDs; визуальная смена текстуры не обязана менять проходимость. Поддерживаемые версии Godot и renderer определяются конкретной поставкой. В этом исследовании её совместимость с нашим GL Compatibility не запускалась. [Import/export на проверенной ревизии](https://github.com/TokisanGames/Terrain3D/blob/185145cedadc93251934aba6f60625050ef155ce/doc/docs/import_export.md).

**Предварительный порядок:** расстановка на текущем 3D preview, затем маленькое сравнение своей кисти и TileMapLayer. GridMap выбирать при реальном требовании модульной 3D-карты. Terrain3D проверять отдельным пилотом высот, не делать обязательной зависимостью editor layer.

## Что обязательно перевести в игровую модель

Визуальные камни могут быть чистой декорацией. Статический утёс компилируется в базовую карту/препятствия. Разрушаемая скала, ворота и ресурс имеют игровую идентичность и footprint; их удаление должно менять симуляцию. Нельзя выводить эти роли из одного наличия `CollisionShape3D`. [Существующее исследование декораций](../large-map-decorations/README.md).

Для высотного поля нужно определить шаг sampling, единицы высоты и производных slope/depth, правило округления и консервативное покрытие препятствий. Пустоты и нависающие поверхности не сворачиваются однозначно в один SurfaceSample. Мост над дорогой требует отдельной модели поверхностей; более богатый editor mesh не снимает это ограничение. Bake от floating geometry следует выполнять контролируемым инструментом и сохранять результат: вычислять его заново на каждом клиенте и считать заранее детерминированным нельзя.

Godot NavigationMesh не является готовой заменой terrain/weighted graph OpenRTS. Из него не следует наличие профильных speed/cost, CanStop, динамических footprint и текущей групповой навигации. Даже NavigationObstacle влияет на avoidance и не означает автоматически изменённый pathfinding. Замена навигации рассматривается отдельно в [runtime-вариантах](runtime-and-ecs.md). [Godot navigation overview](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_introduction_3d.html).

## Подготовка карты: предлагаемый порядок

1. Зафиксировать согласованный снимок авторских данных. Для сцены прочитать только объявленные поля размещений, terrain и references; preview children и окружение не входят в игровые размещения. Чтение Godot-объектов закончить до передачи независимых данных в simulation thread.
2. Проверить ID, типы, владельцев, transform, допустимые численные пределы и ссылки. Разрешить parent transform в систему координат корня карты. Для footprint разрешать только поддержанные повороты; pitch/roll, mirror и scale, меняющие физику без соответствующей модели, отклонять с диагностикой. Нельзя молча менять Model.Size или масштабировать body вслед за картинкой.
3. Нормализовать координаты один раз. Нынешнее соответствие — Godot `(x,y,z)` → OpenRTS `(X,Elevation,Y)` с множителем 1024. Выбрать правило округления; показывать итоговую точную позицию и ошибку границ. Snap кисти и точная позиция юнита независимы. Для далёких координат нужна проверка float precision; integer source предпочтительнее накопления округлений при каждом открытии.
4. Сохранить authoring ID и отдельный явный порядок композиции. Дублирование экземпляра создаёт новые IDs размещений; связанные subscene IDs получают однозначный контекст экземпляра. Переименование Node не меняет identity. Brush order и object spawn order сохраняются согласно версии формата, а не сортируются автоматически «для детерминизма».
5. Преобразовать поддержанные данные в общий вход подготовки. Первый пилот может выпускать существующий M1 и загружать его; расширенный формат не должен дублировать проверки `MapMatch.CreateWorld`. Для нового initial HP/facing/regions сначала определить семантику и версию.
6. Построить временный мир на owner thread, проверить размещения и зависимости. Собрать диагностику с authoring ID/путём/полем. При ошибке освободить мир, не запускать матч и не публиковать частичный результат. Физические конфликты проверяет наша геометрия, даже если Godot разрешил поставить картинку.
7. Записать независимый результат атомарно вместе с версией схемы/компилятора и идентификацией игровых зависимостей. Preview и запуск должны использовать один результат; отладочная карта authoring ID → EntityId хранится отдельно от боевого состояния, если не влияет на правила.

Для M1 экспорт ограничен полями, которые формат действительно принимает. Список neutral objects skirmish нельзя превращать в произвольную расстановку армий; для этого подходят fixture или отдельное согласованное расширение.

## Сохранение, сборка и lifecycle редактора

В B нужно решить, где хранится независимая сборка: версионируемый артефакт рядом с исходником либо воспроизводимый build output, который CI создаёт до .NET headless. `.godot/imported` — кэш Godot, а не надёжная поставка для независимого потребителя. При отсутствии Godot build environment готовый артефакт должен быть доступен; иначе такую конфигурацию нельзя назвать независимой сборкой из исходников.

Актуальность проверяется по версии компилятора и всем игровым зависимостям: scene/resource inputs, referenced subscenes, используемым definitions, brushes и правилам преобразования. Картинки и чисто визуальные overrides исключаются из gameplay identity, но могут иметь свою версию. Хеш сырого `.tscn` не равен gameplay fingerprint.

Нужен один путь подготовки для обычного запуска, F6/выбранной сцены и export/CI. Один `EditorExportPlugin` этого не обеспечивает: его callbacks относятся к export, а customization использует свой кэш и configuration hash. Hook экспорта можно использовать для проверки/упаковки результата и исключения authoring nodes; корректность повседневного запуска должна обеспечиваться тем же компилятором. [Export plugin](https://docs.godotengine.org/en/stable/classes/class_editorexportplugin.html), [CLI/headless export](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html).

`[Tool]` выполняется внутри редактора. Создание мира в каждом setter и изменение сцены без undo сделают работу медленной и хрупкой. Предлагается дешёвая локальная проверка при редактировании, отложенная полная проверка и явный запуск preview-сессии. Сессия освобождается при закрытии сцены, отключении плагина и смене проекта; повторная сборка C# не должна оставлять работающий поток.

Сохраняемые markers и временные preview nodes нужно различать. У сохраняемых дочерних узлов корректно задаётся scene owner; временная графика не должна случайно попадать в файл. Это отдельная семантика Godot `Node.Owner`, не игровой владелец юнита. [Node ownership](https://docs.godotengine.org/en/stable/classes/class_node.html#class-node-property-owner).

## Группы, зоны и сценарии

Повторно используемая авторская группа — набор размещений с offsets и собственным контекстом IDs. Она не обязана быть runtime-родителем юнитов и не задаёт сохранение строя. MoveGroup и размещение prefab решают разные задачи.

Зоны могут начинаться как именованные прямоугольники/круги и ссылки на авторские объекты. Но триггер «когда противник вошёл — создать подкрепление» требует выполнения в симуляции: определённая фаза тика, устойчивый порядок, команды, state и позднее save/restore. Godot `Area3D`/signals полезны для редакторского выбора и косметики; перенос их overlap callbacks в authoritative правила изменит границу исполнения.

Первый срез не должен включать универсальный visual scripting. Достаточно данных зон и одной конкретной игровой проверки, если появится потребитель. Каталоги, карта, сценарные правила и runtime save остаются различными документами; текущий render frame не является сохранением мира.
