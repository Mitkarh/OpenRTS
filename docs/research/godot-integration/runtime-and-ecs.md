# Runtime Godot, тесная интеграция и ECS

[Обзор](README.md) · [Авторские инструменты](authoring.md). Проверка внешних проектов — чтение документации, исходников и GitHub API на 12 ноября 2026 года. Их сборка, импорт в наш проект и сравнительные замеры не выполнялись.

## Что даёт более тесная интеграция во время игры

Работа в редакторе может оставаться тесной при независимом runtime. Но есть и отдельные причины использовать больше Godot во время матча:

- окружение со светом, материалами, частицами, звуком и анимацией;
- сложные представления отдельных объектов, для которых готовая сцена удобнее текущего sprite backend;
- кинематические сцены, камера, UI и локальные интерактивные инструменты;
- просмотр запущенных сущностей в редакторской панели и переход к их исходным размещениям;
- Godot physics/navigation как осознанный backend конкретной игры либо независимой косметической механики.

Эти возможности имеют разную цену. Сложная визуальная сцена редко требует передачи ей HP, очередей производства и правил движения. Замена authoritative физики или навигации, напротив, меняет алгоритмы и модель времени. Объединять оба изменения в один «Godot adapter» без описания владения опасно.

## Вариант C: независимый RTS-мир и более богатые views

Предлагаемая модель: Frent и системы OpenRTS владеют состоянием; Godot получает EntityId, опубликованные позы и необходимые визуальные сведения. Большинство объектов рисуется пакетно. Для отдельных типов или выбранных объектов адаптер создаёт сцену представления и связывает её с EntityId. Косметическая анимация и эффекты работают в Godot, а попадания и доступность действий определяет симуляция.

| Данные или действие | Владелец | Направление связи |
| --- | --- | --- |
| Позиция, HP, приказ, cooldown, производство | OpenRTS | Публикация копий в кадре/диагностике |
| Интерполяция, material, particles, звук | Godot view | Чтение кадра и событий |
| Клик, кнопка ability, тестовая команда | Хост Godot | Команда в session, затем результат из мира |
| Статическая проходимость и footprint | OpenRTS | Подготовленные данные карты и игровые изменения |
| Выбор в редакторе и выделение runtime entity | Editor/debug UI | Authoring ID ↔ runtime EntityId, без ECS refs |
| Полёт осколков без игрового влияния | Godot, если выбрана косметическая физика | Событие создаёт эффект; обратного урона нет |

Важно определить lifecycle view: событие Spawn/Destroy, исчезновение из доступного наблюдения, смена типа, загрузка в транспорт, смена сцены и завершение сессии. Привязка к последней позиции вместо EntityId может перепутать объекты. View не должен превращаться во вторую изменяемую копию игрового state.

Однонаправленный render update не означает один callback на каждый sprite. Текущий `SpriteWorldView` уже применяет пакетные данные. Для анимированных 3D-моделей возможны отдельные сцены, instancing и специализированные animation backends; пригодность нынешних плоских quads для них не доказана. [Текущая реализация](../../../src/OpenRTS.Godot/Rendering/SpriteWorldView.cs).

Godot предоставляет низкоуровневые Servers API в обход SceneTree. MultiMesh снижает стоимость большого числа одинаковых мешей, но видимость оценивается для всего набора, а не каждого экземпляра. Для больших карт стоит проверить пространственные чанки, подбор batch keys и стоимость обновления буферов. Нынешний материал/texture batch не доказывает готовое culling больших карт. [Servers](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html), [MultiMesh](https://docs.godotengine.org/en/stable/classes/class_multimesh.html).

Чанки рендера могут выгружаться независимо от симуляции. Если выгрузить сами игровые деревья/здания только потому, что камера далеко, изменятся пути, ресурсы, обзор и бой. Streaming игрового состояния требует другого исследования.

### Потоки и время

Активный SceneTree Godot не потокобезопасен. Поэтому работающий simulation thread не должен напрямую обновлять Node/Resource; существующая граница кадров здесь подходит. Некоторые server API поддерживают потоки при своих условиях, но это не разрешает передавать им владение игровым состоянием автоматически. [Thread-safe APIs](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html).

Для первого среза следует сохранить tick/session OpenRTS. Если preview запускает `World.Step` вручную в контролируемом последовательном режиме, это отдельный host режим с теми же правилами, а не новая симуляция внутри `_Process(delta)`. Перенос на `_PhysicsProcess` требует определить command boundaries, паузу, догоняющие тики и публикацию; одинаковая nominal frequency сама по себе не доказывает эквивалентность.

Editor debugger может показывать производные сведения о выбранной сущности через сообщения между игрой и редактором. Это не автоматическая поддержка Frent: понадобится диагностическая проекция. Её лучше делать по выбранным IDs и с ограниченной частотой, а не сериализовать весь ECS каждый тик. `FrameLease` и spans нельзя хранить в editor callbacks после Dispose. [Debugger API](https://docs.godotengine.org/en/stable/classes/class_editordebuggerplugin.html), [FrameExchange](../../../src/OpenRTS.Gameplay/Hosting/FrameExchange.cs).

## Вариант D: Godot становится исполнителем игровых механик

В наиболее тесном варианте юниты или их механики живут в Godot Nodes/Resources, столкновения рассчитывают PhysicsServer, пути — NavigationServer, а события идут через signals. Это может сократить разработку игры, чьи основные задачи хорошо совпадают с Godot: физические взаимодействия, ручные анимационные сцены, небольшое число сложных акторов, Godot-centric scripting и multiplayer.

Преимущества реальны: меньше собственных обвязок для встроенных систем; проще использовать готовые Godot assets; почти весь gameplay виден привычными инструментами. При этом переиспользование собственного RTS navigation/combat уже не получается бесплатно. Нужно выбрать для каждой механики одного владельца. Поддерживать одновременно Frent HP и Resource HP либо два независимых расчёта столкновения — плохой способ получить переносимость.

Навигация Godot поддерживает navmesh, регионы, связи и avoidance. Это серьёзная альтернатива для исследования, особенно для преимущественно статичных больших открытых областей. Но её контракт не совпадает с нашим weighted terrain, общими полями/деревьями, точными телами и композициями footprint. Изменения NavigationServer синхронизируются по physics frame; такой backend требует явной точки согласования с тиком OpenRTS. [Обзор навигации](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_introduction_3d.html), [синхронизация сервера](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationservers.html).

`IGridPathfinder` в Core — контракт сеточных стоимостей, а не готовый интерфейс для arbitrary navmesh movement. Нельзя объявить NavigationServer drop-in реализацией только из-за общего слова pathfinding. Потребуются новый контракт пути или адаптация со своими ограничениями, и проверки всех зависящих механик. [Решение 028](../../decisions/028-navigation-route-planner.md), [Core boundary](../../decisions/023-core-and-gameplay.md).

PhysicsServer как источник поз и контактов также требует согласовать численное представление, тела, swept collision, порядок урона и правила воспроизведения. В исследованных источниках не установлена гарантия эквивалентного детерминизма с OpenRTS. Это ограничение доказательств, а не утверждение, что любая физика Godot непригодна для стратегии.

Godot headless позволяет исполнять такую игру без окна. Но это остаётся зависимостью от Godot runtime и не тождественно существующему самостоятельному .NET headless. Если другая игра должна работать на другом движке, Godot-owned механики придётся заменять или переносить. [Command line/headless](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html).

**Когда стоит выбрать D:** после отдельного решения, что Godot-only продукт и конкретные встроенные механики важнее сохранения нынешней архитектуры. Сам запрос на размещение юнитов в редакторе такого решения ещё не требует.

## Нужна ли GDExtension

Нет, для обычных C# Nodes, Resources, editor plugins и вызова нашей .NET-симуляции достаточно Godot .NET. GDExtension предназначена для native shared libraries и позволяет подключать их без пересборки самого Godot. Она уместна при необходимости native C/C++ библиотеки или измеренного узкого места на этой границе, но не является обязательным способом оформить C#-адаптер. [GDExtension](https://docs.godotengine.org/en/stable/engine_details/engine_api/gdextension/what_is_gdextension.html), [текущий sandbox project](../../../sandbox/OpenRTS.Sandbox.csproj).

Перенос Frent/OpenRTS в native boundary ради доступа из GDScript добавит marshalling, платформенные бинарники и поддержку ABI. Для редких команд и опубликованных данных можно рассматривать узкую Godot-facing оболочку в существующем .NET-проекте. Совместимость конкретных Variant-параметров и GDScript API такой оболочки необходимо проверить; весь generic ECS наружу публиковать не требуется.

## ECS-проекты: разные модели интеграции

### Frent внутри Godot .NET

**Наша существующая основа.** Данные и queries независимы от SceneTree, фазы вызывает OpenRTS. Локальный предыдущий probe уже проверил Frent `0.9.1-beta` в Godot `4.7.2/net10.0`; это историческая проверка API, не новый benchmark данного исследования. Массовая миграция runtime state завершена согласно решению 019. [Выбор ECS](../ecs-selection/README.md), [probe](../ecs-selection/probe/README.md), [интеграция](../../decisions/019-ecs-integration.md).

Что требуется дополнительно: authoring wrappers, диагностика и компиляция. Замена ECS этих работ полностью не устраняет: даже встроенная библиотека не знает наших terrain profiles, actions, порядка размещений и content fingerprint.

**Оценка:** сохранить. Повторно открывать выбор при доказанном ограничении текущего ECS или значимом измеренном выигрыше всего pipeline, а не ради сходства редакторских полей с компонентами.

### GECS

**Проверенная ревизия:** `8d2d2b2ddc21b2825712e17419192cedca3d4dd3`, 18 сентября 2026; `plugin.cfg` указывает `9.3.4`. README требует Godot `4.6+`. При этом пример установки в README ещё ссылается на ветку v8; это не основание считать исследованную поставку восьмой версией.

В исходнике `Entity` наследуется от `Node`, `Component` — от `Resource`; экспортируемый `component_resources` связывает scene authoring с компонентами. Есть queries, редакторские средства и debugger. Следовательно, это тесная интеграция через объектную модель Godot, а не готовый Inspector для Frent. [Entity](https://github.com/csprance/gecs/blob/8d2d2b2ddc21b2825712e17419192cedca3d4dd3/addons/gecs/ecs/entity.gd), [Component](https://github.com/csprance/gecs/blob/8d2d2b2ddc21b2825712e17419192cedca3d4dd3/addons/gecs/ecs/component.gd), [README](https://github.com/csprance/gecs/blob/8d2d2b2ddc21b2825712e17419192cedca3d4dd3/README.md), [plugin.cfg](https://github.com/csprance/gecs/blob/8d2d2b2ddc21b2825712e17419192cedca3d4dd3/addons/gecs/plugin.cfg).

**Что полезно:** изучить UX компонентов и выборочную диагностику. **Цена внедрения:** перенос или двойное хранение наших компонентов и правил, Godot lifecycle и отдельная проверка нагрузок. Ни непригодность GECS для 10000, ни преимущество перед Frent здесь не измерены.

Файл LICENSE проверенной ревизии содержит CC0-1.0; нижний текст README на опубликованной странице заявляет MIT. Для учёта происхождения нужно опираться на конкретные файлы поставки, а не короткую подпись README. [LICENSE](https://github.com/csprance/gecs/blob/8d2d2b2ddc21b2825712e17419192cedca3d4dd3/LICENSE).

**Оценка:** референс editor workflow, не кандидат на немедленную замену runtime OpenRTS.

### Godex

**Проверенная основная ветка:** `dafb7b0fc80248fdbe9ea8cfa474ac0a2f9daa73`, последний commit 18 сентября 2023 года. API не помечает репозиторий archived. Это не доказывает отсутствие полезных сторонних forks, но актуальная совместимость основной ветки с нашим Godot не подтверждена. [Commit](https://github.com/GodotECS/godex/commit/dafb7b0fc80248fdbe9ea8cfa474ac0a2f9daa73).

Godex — C++ ECS-модуль Godot. `SCsub` добавляет исходники в `env.modules_sources`; это путь сборки вместе с движком, а не обычный C# addon. README указывает проверенный Godot master commit вместо современного контракта версии; лицензия репозитория — MIT. [SCsub](https://github.com/GodotECS/godex/blob/dafb7b0fc80248fdbe9ea8cfa474ac0a2f9daa73/SCsub), [README](https://github.com/GodotECS/godex/blob/dafb7b0fc80248fdbe9ea8cfa474ac0a2f9daa73/README.md), [setup](https://github.com/GodotECS/godex/wiki/Setup).

**Что полезно:** пример глубокой интеграции ECS и инструментария движка. **Цена:** custom engine build, собственная проверка .NET/export/templates и сопровождение совместимости; миграция с Frent. **Оценка:** исторический архитектурный референс. Современную Godot 4.7-совместимость не считать установленной и не выбирать как основу нашего editor layer.

### Stagehand / Flecs

**Проверенная ревизия:** `c5ecc3b254d30a828fb67d6eb55c07fd15e9dd98`, 21 сентября 2026 года. Старый URL `VerdantInteractive/Stagehand` при проверке перенаправлен в `60k41p/Stagehand`.

Это C++ GDExtension поверх Flecs. README описывает `FlecsWorld`, renderer bridges, Flecs Script и сигналы; отдельно предупреждает о ранней стадии разработки. В дереве есть `entity_composer`; просмотренный скрипт строит GraphEdit с выбором компонентов и undo. Наличие этого UI не доказывает готовое round-trip редактирование всех prefab данных: весь путь сохранения/сборки не прослежен. [README](https://github.com/60k41p/Stagehand/blob/c5ecc3b254d30a828fb67d6eb55c07fd15e9dd98/README.md), [composer](https://github.com/60k41p/Stagehand/blob/c5ecc3b254d30a828fb67d6eb55c07fd15e9dd98/editor_plugins/entity_composer/entity_composer.gd).

**Что полезно:** сопоставимый по идее мост data-oriented simulation → Godot render и отдельный authoring UI. **Цена:** C++ toolchain, Flecs вместо Frent, binary/platform support и новый boundary. Это не plugin, который просто добавит Inspector к нашим C# компонентам. Скорость demos не является измерением навигации и боя OpenRTS.

**Существенное ограничение поставки:** LICENSE содержит BSD-2-Clause **с Commons Clause**, исключающей право Sell в определённых ею случаях. Поэтому этот Stagehand нельзя учитывать как обычную разрешительную BSD/MIT-зависимость. Условия самого Flecs и других зависимостей нужно проверять отдельно; вывод не переносится автоматически на Flecs. [Точный LICENSE](https://github.com/60k41p/Stagehand/blob/c5ecc3b254d30a828fb67d6eb55c07fd15e9dd98/LICENSE).

**Оценка:** архитектурный референс; не добавлять в MIT-основу по результатам этого исследования.

### Другие .NET ECS

Arch, fennecs, EasyEcs и Friflo относятся к отдельному выбору ECS. Наличие примера Godot не означает готовую интеграцию именно с нашим контентом и редактором. EasyEcs и Friflo уже исследованы локально с точными пакетами и ограничениями; здесь их новые версии и зависимости не перепроверялись. Переиспользовать [существующие результаты](../ecs-selection/README.md), не объявляя их рейтингом актуальных версий.

## Сводное сравнение

| Основа | Единица игрового runtime | Откуда связь с редактором | Переносимость от Godot | Решение для OpenRTS сейчас |
| --- | --- | --- | --- | --- |
| Frent + наш адаптер | .NET ECS components | Собственные authoring wrappers и compiler | Сохраняется у симуляции и собранных данных | Основной путь |
| GECS | Node entity + Resource components | Объектная модель и addon Godot | Требует переноса Godot-owned runtime | Изучить UX |
| Godex | ECS в модуле движка | Расширенный custom Godot | Связь со сборкой Godot | Референс, совместимость не подтверждена |
| Stagehand/Flecs | Native Flecs + bridges | Godot extension и отдельные инструменты | Flecs отделим концептуально; конкретный bridge привязан | Референс; лицензия bridge с ограничением |
| Обычные Godot Nodes без ECS | Nodes/Resources и встроенные системы | Нативный workflow | Низкая для игрового кода | Рассматривать только для Godot-first ветки |

Библиотека ECS и интеграция с Godot — два разных выбора. Здесь не найден технический пробел, который требовал бы нового ECS, чтобы размещать юниты в редакторе. Более тесный runtime имеет смысл вводить адресно, начиная с конкретного вида представления или игровой механики и измеряя цену всей связи.
