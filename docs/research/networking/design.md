# Сетевые контракты и алгоритмы

**Статус:** целевой проект; NET1 реализован с уточнениями в [решении037](../../decisions/037-net1-direct-lockstep.md). **Текущий этап:** NET2 завершён в проверенном профиле; действующий pipeline/periodic hashes и версии — [решение039](../../decisions/039-net2-wan-pipeline.md). NET1/ранний NET2 ниже сохранены как исходный проект; NET3 реализован с уточнениями в [040](../../decisions/040-net3-multiplayer-lifecycle.md); NET4+ остаются предложениями. Основания: [поручение и текущее состояние](README.md), [референсы](references.md), [этапы и проверки](roadmap.md), [граница Core/Gameplay](../../decisions/023-core-and-gameplay.md), [сенсоры и знания](../fog-visibility/signatures-and-knowledge.md).

## Продуктовое направление и выбор режима

Уточнение пользователя от 16 ноября 2026: по умолчанию прямой клиентский lockstep по подходу OpenRA/0 A.D./Recoil. Клиенты считают полный мир; внешний сервер не нужен для запуска/завершения игры, replay и восстановления. Сначала развиваем полноценную основную версию, включая зрителей и необязательные сервисы. Доверенный сервер с фильтрацией знаний — последняя дополнительная опция NET8/NET9, а не цель обязательной миграции всех матчей.

Режим задаётся при создании игры и согласуется в descriptor/handshake: обычный клиентский (default) либо защищённый серверный (opt-in, пока не реализован). Аналитика/публикация replay — независимые настройки обычного матча. Account/ticket сервиса поиска не является обязательным условием прямого IP-подключения. TLS и проверки входных данных защищают соединение независимо от режима симуляции и не требуют авторитетного игрового сервера.

## Область и владение

OpenRTS.Network зависит от Gameplay/Core и содержит сетевую границу готовой RTS. Встроенная симуляция сохраняет независимость от сокетов. Типы и wire IDs ниже описывают намерение, а не обещают будущие имена C# классов. Универсальная сеть для любой произвольной игры на Core сейчас не проектируется.

| Роль | Прямой режим | Доверенный режим |
| --- | --- | --- |
| Истинное игровое состояние | Полный SimulationWorld у каждого клиента | SimulationWorld только у доверенного сервера |
| Исполнение игровых правил | Каждый клиент | Сервер; клиентское предсказание не подтверждает результат |
| Хост/координатор | Один клиент назначает места/старт; для 2 участников обмен непосредственный | Отдельный процесс симуляции с учётной identity |
| Поиск матчей | Нет в NET1; затем необязательный каталог, без зависимости прямого IP от аккаунта | Отдельная роль каталога/доступа к серверу |
| Аналитический сервер-зритель | Необязательное воспроизведение журнала и сбор статистики вне barrier игроков | Отдельный анализ записей авторитетной симуляции |
| Получатель | Все команды всех игроков | Разрешённые знания и подтверждения своих команд |

Один owner thread вызывает Step, строит игровой результат, читает/меняет ECS. I/O задачи декодируют ограниченные сообщения и передают собственные immutable данные через bounded очереди. Они не получают Frent refs. При кодировании FrameLease копируется/кодируется внутри using; после Dispose очередь может владеть только независимым буфером. Сеть не удерживает слот кадра до медленного socket write.

## Обязательные инварианты

1. **Identity:** источник Issuer/Player/роли — согласованное соединение; поля из payload не предоставляют права. Issuer0 доступен только локальному сценарию. В первом срезе один peer соответствует одному ненулевому player ID, совпадающему с Issuer для RestrictCommandsToPlayers.
2. **Порядок:** tick → issuer → sequence; sequence положительный, монотонный на issuer в пределах match. EntityId — доменный ID, native ECS handles не передаются. При смене transport connection сохраняется identity участника; старые connection epochs отбрасываются.
3. **Детерминизм:** порядок доставки, I/O callbacks, FPS, wall-clock и порядок jobs не задают игровой порядок. Они могут задерживать продвижение. Согласованный игровой pause/disconnect — отдельная запись на определённом тике.
4. **Ограничения:** размер пакета, строки/списки, суммарный batch, окно будущих тиков, очереди, история, декомпрессия и скорость входа ограничены до дорогой обработки. Нет сетевой полиморфной десериализации .NET типов.
5. **Результат:** принятие входного сообщения, помещение в закрытый tick batch, исполнение и игровой успех — разные состояния. Например, готовый приказ постройки ещё может быть отклонён миром.
6. **Безопасный режим:** клиент не получает скрытую истину в snapshot, журнале, событиях, ID, диагностике, карте или зрительском потоке. Шифрование канала не скрывает сведения от самого получателя.
7. **Отмена:** ожидание пакета отменяемо без Step. Отмена внутри Step делает мир незавершённым по текущему контракту; такой мир не публикуется и не используется для восстановления.

В первом прямом режиме участники доверяют друг другу в отношении хранения полного мира. Checksums обнаруживают случайное расхождение, но не доказывают честность, не устраняют map-hack, автоматизацию ввода или умышленный stall. Хост также может обманывать. Выделенный trusted host должен находиться вне контроля игроков для действия модели доверия.

Режим доверия выбирается до старта: матч, уже раскрывший клиентам полный мир, нельзя сделать секретным переключателем. Разрешённые ранее наблюдения клиент может сохранить навсегда; переход в hidden прекращает выдачу свежей истины, а не стирает уже полученные сведения. Переход зрителя в игрока требует отдельной policy и обычно запрещён после omniscient доступа.

## NET1. Подключение и подготовка матча

**Цель:** не запускать разные правила и не пропускать произвольные WorldCommand в мир. **Вызов:** до первого Step. **Результат:** согласованный descriptor либо закрытое соединение с причиной, без частичного старта.

1. Для NET1 слушать заданный IP/порт и подключаться к нему напрямую. Начальный транспорт — TCP/NoDelay из BCL, length-prefixed framing с явным endian, version и message kind. Чтение учитывает partial reads, EOF, deadline и отмену; длина проверяется до выделения массива. TCP сохраняет поток байт, а не границы сообщений.
2. Обменять protocol major/minor, поддерживаемый режим и версии codec/schema. Неизвестный обязательный тип/major отклонить. Список необязательных возможностей согласовать пересечением. Запуск внешнего кода/загрузка DLL по сети запрещены протоколом.
3. Координатор назначает match ID, player/peer slots и immutable descriptor: build/rules version, gameplay fingerprint, hash исходной карты и сценария, simulation settings/tick rate, seed, игроки/команды, разрешённые команды и delay D. Визуальные модели не обязаны совпадать; их несовпадение не меняет gameplay fingerprint.
4. Каждый участник готовит мир локально через потребителя Content, сверяет descriptor и исходный hash тика0. При несовпадении не вызывать Step. Не считать один catalog fingerprint проверкой всей карты и настроек.
5. Ready относится к digest descriptor. Изменение настроек снимает Ready у всех. Start содержит тот же digest и стартовую эпоху; поздний Ready старого descriptor игнорируется. Только после подтверждённой готовности обоих peers активируется протокол тиков.
6. Включить RestrictCommandsToPlayers до первого тика. Сетевой codec допускает только player intents из whitelist. Spawn, Remove, BlockCell, произвольное изменение owner/credits/conditions и issuer0 не являются player input.

Полный descriptor с seed и исходным сценарием относится к lockstep. В trusted режиме bootstrap отдельный: публичные правила/ресурсы и разрешённая карта, но не секретный RNG seed, скрытые начальные армии, их приказы или server-only scenario data. Если клиент может восстановить скрытый мир из выданного seed/контента, фильтрация дальнейших snapshots уже не решает задачу. Публичность terrain/размещения статических объектов определяется правилами игры; скрытые данные не должны попадать и в устанавливаемый клиенту asset package.

NET1 — тестовая LAN/IP игра; доверенная идентификация аккаунта отсутствует. До публичного WAN режима NET2 требует аутентифицированного шифрованного канала: предпочтительно платформенный TLS с проверкой сертификата либо согласованного fingerprint по внешнему доверенному каналу. Конкретный flow сертификатов выбирается в NET2; отключение проверки сертификата не считается решением. TLS не меняет честность хоста. У LAN/IP прототипа интерфейс явно показывает режим доверительной игры.

**Предварительные лимиты для стенда, не доказанные бюджеты:** control frame ≤64 KiB, строка action ID ≤128 UTF-8 bytes, суммарный tick batch ≤256 KiB с ограниченными chunks, ≤256 команд/issuer/tick, ≤16384 recipients в команде и ограничение суммарных recipients на batch. Для большой selection используется отдельное ограниченное сообщение либо chunking, не неограниченный allocation. Перед NET1 значения проверить по реальному codec: худший batch не обязан помещаться в один frame. Числа меняются версией/descriptor, а не тихо только на одном клиенте.

## NET1. Прямой lockstep двух участников

**Состояние:** подтверждённый локальный Tick, фиксированный D≥1, закрытые batches каждого issuer, окно H≥D+1, локальный ввод ещё не закрытого batch, sequence counters. **Выход:** один полностью согласованный вызов Step либо ожидание/ошибка.

1. На тике0 считать тики1..D−1 согласованно пустыми по descriptor; закрыть и отправить собственный batch для D. При D=1 первый batch сразу относится к тику1. Локальная копия проходит тот же путь приёма, что удалённая.
2. После завершения тика n закрыть batch n+D. Пока batch открыт, UI намерения добавляются в него с возрастающим sequence; после закрытия менять его нельзя. Ввод после закрытия ждёт следующего batch. Начальный D фиксирован на весь матч NET1; live adaptation позднее требует согласованной записи и переноса границы без потерь.
3. Batch содержит match/epoch, issuer, tick, batch sequence, count и команды, включая все дополнительные поля WorldCommand, применимые к разрешённому intent. Кодировать enum через явные wire IDs, не текущий ordinal CommandKind. Пустой batch обязателен. Список EntitySet кодировать канонически и проверять уникальность ID/лимиты.
4. При приёме проверить identity, диапазон tick и sequence, лимиты и схему. Собрать bounded chunks; готовность даёт только полностью принятый batch. Повтор с тем же ключом и теми же байтами идемпотентен; тот же ключ с другим содержимым — нарушение протокола и остановка. Gap по последовательности нельзя заменять пустым вводом.
5. Для next=n+1 дождаться закрытых batches обоих участников. Нет одного batch → состояние WaitingForInput; I/O и UI продолжаются, Step не вызывается. Timeout в NET1 завершает матч с диагностикой; клиент не исключает другого участника и не продолжает самовольно.
6. Объединить в canonical order, назначить Tick/Issuer из согласованного envelope, проверить structural payload до Step. Ошибка формата пакета фатальна для матча NET1; команда, утратившая игровую допустимость, разрешается текущими правилами мира одинаково у обоих.
7. В owner thread выполнить Step ровно один раз; сохранить принятый batch, опубликованные события и контрольный hash в установленной периодичности. Сетевой ack доставки не равен успешному игровому результату.
8. После Step перейти к пункту2. Не накапливать неограниченное wall-clock «отставание» во время сетевой паузы: при восстановлении ограничить catch-up, не менять фиксированную длительность игрового тика.

```text
при входящем batch:
    validate_envelope_and_bounds()
    insert_once_or_compare_existing_bytes()
    wake_owner()
на owner:
    если next tick не готов у всех: ждать сигнал или cancel
    иначе: canonical_commands = close_and_validate(next)
           world.Step(canonical_commands)
           record(next); publish_copies(); seal_own_batch(next + D)
```

**Ручная трасса:** D=2, тики1 пустые. На старте оба закрывают2. После1 закрывают3. A получает B:3 раньше B:2 →3 хранится в окне,2 ждёт; после B:2 исполняется2, затем3. Дубль A:2 не создаёт повторного движения. Пропавший B:2 не превращается в пустой тик.

Существующий Session.Submit не годится: он переписывает stamp по локальному следующему тику. В NET1 создать минимальный сетевой owner-loop вокруг SimulationWorld.Step с явным batch barrier. Публикацию и освобождение мира выполнить по существующим инвариантам. Общий session scheduler извлекать только при подтверждённом повторении; текущую offline Session сохранять. Многопользовательская звезда в NET3 использует координатора для итогового batch и membership, без Byzantine consensus и обещания пережить злонамеренного хоста.

## NET2–NET4. Desync, журнал и восстановление

**Диагностика:** в конце одного и того же тика сравнивать версионированный hash мира вместе с descriptor digest и digest применённых команд. Хранить bounded кольцо последних hashes, batches и параметров окружения; долговременный replay писать потоково с квотой. На первом mismatch остановить продвижение, сохранить первый известный расходящийся тик и локальные отчёты. Не выбирать «честного» игрока большинством hashes. Частоту Report установить замером: существующий полный SHA-256/сериализация может стоить существенно, а не только передачу32байт.

**Replay:** descriptor + начальные данные + все согласованные batches, в том числе пустые, membership/control записи и изменения delay. Проигрывание использует тот же codec/проверки и Step без wall-clock зависимости. Межверсионное воспроизведение не обещается. В прямом режиме replay содержит полную информацию: не распространять его как безопасный live поток наблюдателя.

**Полный checkpoint — отдельная зависимость Gameplay/Core:** на границе тика сохранить canonical runtime, RNG/следующие ID, очереди приказов/производства, projectiles, движения/остатки, состояния способностей/условий/upgrade/transport/flight, fog/sensors/knowledge и отложенные действия. Derived caches перестроить по явно описанному правилу, которое не меняет дальнейшее поведение. Frent handles и spatial buckets не являются форматом сохранения. Полноту доказывает равенство дальнейших hashes непрерывного и восстановленного запуска, включая крайние состояния.

**Возврат lockstep-участника:** проверить resume token и новую connection epoch → выбрать checkpoint K с закреплённой версией → передать chunked snapshot с пределами compressed/uncompressed размеров и digest → применить хвост K+1..T → догнать без рендера с ограничением CPU → сверить hash → подключить к barrier с согласованного будущего тика. До этого participant не задерживает текущий матч. Если catch-up медленнее роста хвоста, взять более новый checkpoint либо отказать; не копить очередь без границы. До checkpoint допустимо воспроизведение от0 для коротких матчей с явным лимитом, а не обещание быстрого rejoin.

При потере соединения NET3 сначала приостанавливает матч. Исключение/AI takeover оформляет координатор на согласованной границе; решение timeout не принимается каждым peer независимо. В базовом варианте потеря хоста завершает матч. Host migration — отдельный поздний этап, требующий истории, epoch/membership и защиты от двух координаторов.

## NET5. Поиск матча и допуск

**Цель:** найти совместимый матч и получить право на конкретное место. **Владелец:** сервис каталога/доступа; состояние боя ему не требуется.

1. Хост регистрирует match ID, поддерживаемые protocol/rules versions, режим доверия, публичные настройки, доступные роли и endpoints. Heartbeat продлевает TTL; исчезнувший хост не оставляет вечное доступное лобби.
2. Поиск фильтрует только публичные поля, совместимость и доступные слоты. Пароль/приглашение не раскрываются в списке. Рейтинг/география позднее влияют на подбор, но не подменяют проверку версии при подключении.
3. Join с учётной session атомарно резервирует слот с коротким сроком. Два запроса на последнее место не создают два действительных назначения. Повтор одного join request ID возвращает ту же резервацию.
4. Выдать role-bound билет с participant/match/slot, сроком, nonce и разрешёнными endpoints. Match host проверяет подлинность, срок и одноразовое погашение; клиентское поле player не заменяет назначение билета.
5. Попробовать прямой путь. При недоступности согласовать выбранный relay; он пересылает ограниченные данные и не становится источником игровых результатов. Резервация освобождается по истечении срока/явному отказу.
6. После handshake матч подтверждает занятое место и публикует обновлённую lobby revision. Изменение важных настроек снова снимает Ready. Вход в уже начатый матч следует отдельной rejoin/spectator policy.
7. Закрытие матча снимает регистрацию. Доверенный результат подтверждает сервер симуляции; отчёт P2P хоста хранится с явной отметкой его происхождения и не считается защищённым рейтингом.

Provider авторизации, способ подписи/погашения билетов, хранение каталога и NAT backend выбираются на этом этапе по реальному потребителю. Это обязанности протокола, а не основание заранее создавать IAM/БД/универсальный сервисный фреймворк.

## NET6. Необязательный сервер-зритель и аналитика

**Цель:** собирать воспроизводимую историю матча для статистики, анализа игры/баланса и поиска признаков читерства, не становясь источником игровых результатов.

1. При создании матча явно выбрать, разрешены ли сбор и публикация данных, live наблюдение либо только послематчевый архив. Поиск игр и сбор аналитики независимы; прямое подключение работает без обоих сервисов.
2. Подключить наблюдателя с идентичностью матча/версий/контента; передать разрешённые начальные данные и журнал команд с checkpoints/hashes. Альтернатива — загрузка законченного replay. Наблюдатель не включается в множество peers, чья готовность разрешает следующий тик.
3. Принимать поток через отдельную bounded очередь. Отставание/отказ сервера прекращает подписку либо переводит её на последующую загрузку архива; не блокирует игрокам отправку команд и Step. Если нужны серверные расчёты, наблюдатель воспроизводит ту же клиентскую симуляцию у себя, без коррекций мира игроков.
4. Проверить полноту и непрерывность журнала, версии и hashes, сопоставить доступные отчёты разных участников. Сохранить происхождение и степень подтверждённости данных, дедуплицировать повторные загрузки по match/source/revision.
5. Рассчитать версионированные метрики экономики, производства, боёв, исходов и применения контента; отделить сырые наблюдения от выводов по балансу и подозрений в читерстве. Совпадение replay не доказывает отсутствие map-hack; один отчёт недоверенного клиента не является удостоверенным результатом.
6. Выдавать аналитические отчёты с учётом роли и времени матча. Live полные записи не должны становиться публичным обходом зрительской policy. Автоматические санкции/изменения баланса требуют отдельной политики и подтверждений, а не следуют из одного подозрения.

Это отдельная роль от client-host, relay и авторитетного сервера. Проверки: работа без наблюдателя, разрыв/отставание сервиса, неполные и противоречивые replay, повторная загрузка, ограничения доступа. Ни одна ошибка сервиса не меняет игровые результаты.

## NET8. Приём команд доверенным сервером (последний дополнительный режим)

**Цель:** клиент сообщает намерение, сервер выбирает допустимое исполнение. **Вызов:** I/O admission, затем owner thread до соответствующего Step.

1. После проверки канала связать session с account/participant/ролью. Match ticket ограничивает матч, срок и роль, одноразовое использование проверяется сервисом. Reconnect подтверждает ту же identity, но инвалидирует старое соединение.
2. Принять client command ID и желаемый тик лишь как hint. Проверить replay window, rate/bytes/recipients и whitelist. Сетевое состояние не даёт issuer0/admin. Дубликат возвращает прежний bounded результат, не повторяет расход ресурсов.
3. Сервер назначает canonical issuer, sequence и будущий tick по фиксированному правилу admission. Уже закрытый тик не переоткрывается, поздний input переносится или отклоняется с подтверждением. Порядок внутри назначенного тика сохраняет issuer/sequence; журнал сервера фиксирует выбранное назначение.
4. В момент исполнения проверить владение, актуальную видимость/адресуемость цели, доступность способности, платежи и физические ограничения через Gameplay. Нельзя принять клиентский HP, урон, попадание, результат поиска пути или баланс кредитов как истину.
5. Выполнить Step без ожидания пустого batch от каждого клиента. Медленный/пропавший клиент получает установленную policy продолжения без команд/отключения, а не останавливает сервер бесконечно.
6. Подтвердить исполненный command ID и дать разрешённый результат. Ошибки скрытых целей имеют одинаковый внешний ответ; подробная диагностика остаётся у сервера. Предсказание клиента сверяется с этим подтверждением.

AI в доверенном режиме считает сервер. В lockstep будущий AI либо детерминированно считается всеми, либо один назначенный участник публикует его команды под согласованной identity. Это отдельная policy; текущий collectCommands с reserved issuers нельзя подключать независимо у каждого peer и получать дубли.

## NET8–NET9. Репликация знаний без полного мира

**Состояние сервера:** разрешения viewer, известные клиенту wire handles, подтверждённая baseline revision, актуальные наблюдения и очередь надёжных событий. **Выход:** snapshot/delta только разрешённых полей. Это новый DTO, не сериализация FrameLease.

1. После завершения симуляции вычислить знания получателя через существующие сенсоры. Авторизация viewer берётся из session; запрос viewer0/другого player не переключает права. Отсутствующая fog-конфигурация не открывает весь мир молча: матч имеет явную visibility policy.
2. Спроецировать разрешённые entities/contacts/terrain/economy/events. Разделить собственные полные данные, наблюдаемые live поля, устаревшую память и анонимный radar contact. Контакт не обязан иметь EntityId и не подтверждает скрытую личность объекта.
3. Выдавать wire handle только при первом разрешённом наблюдении. Mapping существует у сервера и получателя; последовательность domain EntityId и список скрытых ID не передаются. Повторное использование handles требует generation. Стабильность после потери видимости зависит от правил памяти/идентификации, а не от удобства codec.
4. На переходе visible→hidden послать прекращение live обновлений и разрешённую память последнего наблюдения. Не отправлять истинную смерть/текущую позицию скрытого объекта. При новом появлении сбросить Previous к текущей разрешённой позиции, чтобы интерполяция не раскрывала путь через туман.
5. Фильтровать ссылки внутри orders/weapons/projectiles/carrier/airbase, исходные координаты эффектов, звуки, HP, состояния, player economy и события, а не только список entities. Снимок карты делит публичный base terrain и разрешённые динамические изменения: истинный effective NavigationGrid со скрытыми footprint не отправлять целиком.
6. Применить camera/LOD/bandwidth policy только после permission filtering. Camera — hint приоритета внутри разрешённых данных, не источник права видеть. Общую сериализацию разрешать лишь получателям с одинаковой policy и знаниями.
7. Построить delta относительно **подтверждённой** baseline, пометить snapshot ID/base ID/server tick. Потеря baseline → запрос bounded keyframe; пропущенная delta не применяется к случайному состоянию. Смену поколений, hide/despawn и важные события доставлять надёжно либо через подтверждаемый повтор; позы допускают latest-wins. Очереди на slow consumer ограничены, промежуточные позы можно сбрасывать.
8. Клиент атомарно применяет revision к своей реплике знаний, интерполирует разрешённые позы и отображает подтверждения команд. Он не запускает полный SimulationWorld ради «досчёта» отсутствующих врагов. Косметические события имеют ID и защиту от повторного проигрывания.

**Проверяемая гипотеза защиты:** для двух серверных миров с одинаковой разрешённой историей наблюдений, но разными скрытыми объектами нормализованный исходящий прикладной поток игроку одинаков. Нормализация исключает nonce/служебные sequence, но не скрывающие утечку поля. Проверять initial state, snapshots, events, отказы, replay и reconnect. Timing/размеры пакетов тоже могут давать сведения: измерить их отдельно; padding/фиксированные интервалы вводить при установленной модели угроз и цене. Абсолютное устранение всех побочных каналов пока не обещается.

## Зрители основной версии и поздние серверные возможности

Обычные lockstep-зрители, replay и rejoin реализуются в NET4/NET7 без зависимости от защищённого режима. Сервер-зритель NET6 использует те же механизмы и может быть полностью отключён. Следующие правила filtered rejoin, гарантированной задержки выдачи и восстановления авторитетной симуляции относятся только к позднему NET8/NET9.

- **Player rejoin в trusted режиме:** новый filtered keyframe знаний + разрешённые события/подтверждения после него. Полный checkpoint сервера клиенту не выдаётся. Полный save/restore нужен для восстановления самого сервера, а не для простой замены клиентской реплики.
- **Наблюдатель:** отдельная роль с явно заданным player POV, team POV или omniscient policy. Live omniscient spectator может сообщать противнику сведения; ranked требует запрета либо серверной задержки.
- **Задержка наблюдателя:** сервер удерживает данные до T−delay. Слать текущие данные и просить UI показать позже небезопасно. Snapshot, события, команды, чат/метаданные матча и переходы POV должны следовать одной временной policy. Медленный зритель не задерживает игроков; его буфер имеет квоту.
- **Replay сервера:** полный внутренний журнал доступен администраторам; публичный live/послематчевый экспорт подчинён правилам матча. Запрос полного replay не является обходом spectator policy.
- **Падение сервера:** durable checkpoint + journal, replay до подтверждённой commit boundary, новая session epoch и reconnect. Для недублирования платежей/задач сохранять idempotency state и границу подтверждений. HA/резервирование — после измерения стоимости и определения RPO/RTO.

## Альтернативы и открытые решения

| Вариант | Польза | Цена и решение сейчас |
| --- | --- | --- |
| Full mesh peers | Нет единственного маршрутизатора | O(P²) соединений, NAT и согласование membership; только прямые2, затем звезда |
| Host relay lockstep | Мало изменений к первому прототипу | Хост/клиенты знают полный мир; полезный отдельный режим |
| Server lockstep + полная клиентская симуляция | Сервер проверяет результаты | Скрытая истина остаётся у клиента; не конечная защита от map-hack |
| Authoritative snapshots/knowledge | Контроль выдачи и результатов | Стоимость сервера/трафика; целевой защищённый режим |
| Rollback полного RTS мира | Меньше задержка визуального ответа | Нужны полные снимки, переисполнение тяжёлых тиков и политика событий; отложить |
| Клиент считает скрытую навигацию/бой | Возможное снижение server CPU | Раскрывает данные или требует проверки, сопоставимой с вычислением; исключено из базовой защиты |
| TCP/TLS | BCL, надёжный поток, простая первая диагностика | Head-of-line при потере; NET1/2 кандидат, не окончательный транспорт репликации |
| QUIC либо готовый reliable UDP | Независимые потоки/datagrams | Поддержка desktop/runtime, лицензии, зависимости и эксплуатация требуют отдельного spike |

Открыты: целевое число игроков, допустимые RTT и задержка управления, длительность матча/истории, ОС/архитектуры для lockstep, provider NAT/relay, бюджет trusted server и uplink, политика sharing vision и ranked spectators. Эти вопросы не блокируют NET1. Пороговые значения установить baseline-замерами; источник истины и фильтрацию не менять молча ради ускорения.
