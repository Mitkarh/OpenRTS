# Сетевой слой OpenRTS

**Дата:** 16 ноября 2026. **Статус:** NET1 реализован как конечный headless lockstep двух клиентов; [контракт037](../../decisions/037-net1-direct-lockstep.md), [проверки](../../verification/037-net1.md). NET2 с pinned TLS, UI и WAN pipeline реализован: [контракт038](../../decisions/038-net2-live-direct-matches.md). Защищённый сервер по-прежнему отложен.

Поручение и уточнение пользователя от 16 ноября 2026: основная версия — прямой обмен командами и полная симуляция на клиентах, ближе к OpenRA/0 A.D./Recoil. Сервер необязателен: помогает искать игры и может участвовать зрителем для статистики, анализа партий, корректировки баланса и поиска читеров. Безопасный режим с доверенным сервером — последняя дополнительная возможность, включаемая при создании игры; по умолчанию выключена. Основная реализация ведётся в [OpenRTS.Network](../../../src/OpenRTS.Network/README.md).

## Режимы и приоритеты

1. **Основной, по умолчанию — клиентский lockstep.** Участники обмениваются закрытыми пакетами команд на будущие тики; каждый считает полный мир. Прямое подключение не требует внешнего сервиса. Для нескольких участников клиент-хост может координировать обмен. На этой модели строятся полноценная игра, восстановление, replay и зрители.
2. **Необязательные сервисы основной версии.** Поиск игр, помощь подключению/relay и сервер-зритель для сбора и воспроизведения матчей. Аналитический наблюдатель не входит в игровой tick barrier, не корректирует мир и не останавливает матч при своём отказе. Анализ может выявлять подозрения/нарушения, но не гарантирует обнаружение чтения скрытого мира из памяти клиента.
3. **Последняя дополнительная опция — безопасный режим.** При создании матча выбирается отдельный режим с авторитетной серверной симуляцией и фильтрованными знаниями клиентов. Он не заменяет основной lockstep и не является условием выпуска его возможностей. Переход уже начатого полного lockstep-матча в секретный режим не обещается.

Каталог игр, relay, сервер-зритель и доверенный сервер симуляции имеют разные обязанности. Они могут размещаться вместе, но наличие сервиса поиска/аналитики не превращает обычный матч в авторитетный. [Референсы](references.md) · [контракты](design.md) · [обновлённые приоритеты NET0–NET9](roadmap.md).

## Текущее основание OpenRTS

Изучен checkout на основе `f0b88b37c871ea451672203c4f819d1b1fbbf1d9`, включая существующие локальные изменения авиации/посадки и представления. Они не принадлежат этой работе и не пересматривались. Проверены относящиеся к сети пути по исходникам; референсные игры не запускались.

| Существующий механизм | Подтверждение | Следствие для сети |
| --- | --- | --- |
| Фиксированный тик, один владелец мира, сначала валидация batch | [Simulation.Step](../../../src/OpenRTS.Core/Simulation/Simulation.cs) | Сеть должна разрешать следующий тик до вызова Step; сетевой поток не меняет ECS |
| Сортировка по Issuer/Sequence, положительный Sequence, точный следующий Tick; duplicate отклоняется внутри batch | [CommandBatch.Replace](../../../src/OpenRTS.Core/CommandBatch.cs) | Межтиковая дедупликация и привязка к соединению ещё нужны |
| Live Submit переписывает Issuer=1, затем Tick=world.Tick+1; scripted issuer=0 | [общая SimulationSession](../../../src/OpenRTS.Core/Hosting/SimulationSession.cs) | Нельзя просто пересылать пришедший WorldCommand через текущий Submit |
| Есть opt-in RestrictCommandsToPlayers; для ненулевого issuer проверяются владельцы и whitelist приказов | [PlayerCommands](../../../src/OpenRTS.Gameplay/Orders/SimulationWorld.PlayerCommands.cs) | Повторно использовать игровую policy, но identity назначать на сетевой границе; issuer0 никогда не принимать из сети |
| Есть отдельная проверка доступности цели, затем CommandDenied | [ApplyCommand](../../../src/OpenRTS.Gameplay/Simulation/SimulationWorld.cs), [видимость](../../../src/OpenRTS.Gameplay/Visibility/SimulationWorld.Visibility.cs) | В сетевых отказах исключить oracle для скрытых целей; порядок игровых проверок сохранить |
| Report строит SHA-256 сериализуемого состояния; есть журнал применённых команд | [SimulationWorld](../../../src/OpenRTS.Gameplay/Simulation/SimulationWorld.cs), [Session](../../../src/OpenRTS.Core/Hosting/SimulationSession.cs) | Основа desync-диагностики; ни хеш, ни графический кадр не являются save/restore |
| Viewer-кадры, контакты и фильтрация событий уже существуют | [FrameExchange](../../../src/OpenRTS.Gameplay/Hosting/FrameExchange.cs), [Filter](../../../src/OpenRTS.Gameplay/Visibility/FrameExchange.Visibility.cs), [FogEventVisibility](../../../src/OpenRTS.Gameplay/Visibility/FogEventVisibility.cs) | Источник семантики будущей выдачи; не готовый безопасный wire DTO |

В `Filter` сохраняются `Grid`/`BaseGrid` истинного мира. `AcquireLatest(0)` даёт общий кадр, а при отсутствии списка FogPlayers фильтрация не выполняется. Поэтому сериализация существующего lease целиком не является безопасным серверным протоколом. Полный snapshot/restore пока отсутствует по текущей архитектуре; rejoin с контрольной точки зависит от отдельной работы над сохранением.

## Что сравнивалось

OpenRA выбран за C#, разделение графического/сетевого тика и близкий домен; 0 A.D. — за барьеры команд и восстановление подключения; Recoil — за массовую RTS, dedicated relay и воспроизведение потока; Mindustry — как RTS-гибрид с передачей состояния по видимости. Последний отличается наличием управляемого игроком персонажа, поэтому его модель доверия к координатам не переносится в OpenRTS.

Метод: статические трассы выбранных функций, проверка вызываемых ветвей, официальная документация Recoil. Это направленное сравнительное исследование, не аудит безопасности этих проектов. Версии, ссылки и пределы чтения находятся в [реестре источников](references.md). Никакой GPL код, переводы функций или сторонние зависимости в MIT модуль не перенесены.

## Основные развилки

- Два клиента сначала связываются непосредственно; для 3+ участников реализована звезда через клиент-хост. Хост остаётся участником с полным миром, а не доверенной стороной.
- Для первого LAN/IP прототипа предлагается TCP с ограниченным framing. Для WAN и state replication транспорт выбирается после измерения head-of-line задержек; собственный reliable UDP заранее не строится.
- Ранний replay — initial match descriptor + команды от тика0. Контрольные точки нужны позднее для дешёвого rejoin, перемотки и восстановления сервера.
- Защищённый режим требует серверных расчётов навигации, боя, экономики, сенсоров, RNG и всех взаимодействий со скрытыми объектами. Клиентские расчёты допустимы как подсказки/предсказание без права менять истину.
- Переход будет отдельным сетевым режимом, а не обещанием совместимости первого wire-протокола. Версии согласуются при подключении, несовместимые режимы отклоняются.

NET3 реализует несколько участников, согласованные membership/disconnect/pause и AI policy: [контракт040](../../decisions/040-net3-multiplayer-lifecycle.md), [проверки](../../verification/040-net3.md). Следующий основной этап — NET4: snapshot/restore и восстановление. NET1 работает в headless-стенде через loopback TCP с барьером тика и desync-проверкой. [WAN-результат039](../../verification/039-net2-wan.md). Подробный backlog и ограничения каждого этапа: [roadmap](roadmap.md).
