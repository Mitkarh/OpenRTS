# Проверки перед изменением архитектуры

Это программа будущих пилотов. Исследование опирается на чтение текущего кода и опубликованные проверки B0–B3. Прототипы, экспорт и новые измерения в рамках исследования не запускались.

## 1. Дойти до первого внешнего потребителя B4

В чистом Godot .NET проекте завести две простые не-RTS сцены и переход в боевую `PackedScene`. Для карты использовать полноценную entry сцену и её compiled проекцию с B4. Контент может быть небольшим, например один отряд, два владельца, проходимая и непроходимая зоны. Сохранить для сравнения запуск той же проекции обычным headless. Использовать готовые инструменты B0–B3 для авторской части. Исходники и ассеты стороннего потребителя могут быть независимы от sandbox.

**Проверки.**

- Игра открывает бой, принимает приказ после получения фокуса, возвращает результат и позволяет открыть следующий матч. Esc обрабатывает хост. Хоткеи родительского экрана и локальная пауза ведут себя предсказуемо.
- Хост уходит во время загрузки, во время боя или после получения результата. Старые callbacks и команды не воздействуют на новый бой. Выход в обычном сценарии не даёт заметной задержки. Для повторных входов сравнить число worker threads, используемую память и Godot objects после нескольких циклов прогрева. Проверить отсутствие роста, учитывая кэши и время освобождения.
- Сцена запускается в чистом проекте с выключенным editor addon. После чистого экспорта игра находит карту, её compiled данные и ресурсы без checkout по специальному относительному пути. Для распространяемого профиля проверить запуск из экспортированной сборки, включая другие desktop ОС только если они входят в профиль пилота.
- Необязательный второй шаг — открыть два экземпляра, а также встроить один как `SubViewport` под HUD. Проверить разный фокус, общий фон, разрешения, отдельные выборы и отсутствие общих изменяемых ресурсов. Если один экземпляр в полноэкранной сцене удовлетворяет проекту знакомых, стоимость поддержки двух экземпляров можно оценить отдельно.
- Прогнать один и тот же журнал с тем же recipe из встроенного и .NET headless хостов. Сравнить gameplay hashes/checkpoints и итог, а не момент получения кадра. Поменять render FPS и число workers. Для Godot-only dedicated варианта дополнительно проверить headless Godot export по тому же журналу.

**Решение по результату.** Если вход, выход, поставка и паритет проходят, есть основание считать режим переносимым между Godot .NET проектами в заявленном профиле. Если зависимость от sandbox основная преграда, выделять тот wiring, который дублируется у потребителей. Если преграда относится к совместному миру, проверить одну конкретную механическую связь до инвестиций в упаковку.

## 2. Измерить выигрыш для разработчиков и авторов

Выполнить одинаковый change request двумя путями. Например, добавить карту с проходом и воротами, передвинуть точку старта, переиспользовать декорации из другой сцены, поменять визуальную анимацию ворот, привязать их к игровому событию, собрать и пройти встречу. Сравнить текущий способ с нативной entry сценой и обёрткой режима. Использовать одинаковые gameplay требования и один набор арта.

Снять время до первого успешного запуска и время на повторную правку. Сравнить число файлов/инструментов, ручных преобразований, случаев stale compile, сложность merge и объём production кода, который можно удалить после пилота. Включить чистую сборку/export и диагностику намеренной ошибки в одном размещении. Узнать у автора, какие операции потребовали C# и почему. Сцену вправе редактировать сам геймдизайнер, поэтому измерять весь путь от правки до playtest, включая передачу задачи программисту.

**Решение по результату.** Продуктовый Godot-first выбор окупается, если открывает повторяемый рабочий процесс и снимает регулярную работу сопровождения на стороне продукта. Потребность во втором графическом хосте оценивать по названному потребителю и его требованиям. Если экономия только в названии платформы, границу .NET можно сохранить без новой абстракции.

## 3. Проверить одну нативную игровую подсистему

Выбирать функцию с конкретной болью или нужной механикой. Хороший первый эксперимент — Godot navmesh для небольшого отряда в общей 3D-сцене либо Godot bake статических препятствий с компиляцией в независимую карту. Эти два применения проверяют разные зависимости. Для runtime-варианта сравнить нынешний baseline, компактный Godot gameplay и, только при необходимости, низкоуровневую реализацию через Servers. Одни и те же карта, стартовые позиции, команды, оборудование и конфигурация сборки. Прогрев отделить от первого приказа и первой динамической правки карты.

| Что измерять | Сценарий |
| --- | --- |
| **Качество и семантика** | Узкий проход, акторы двух размеров, цель вне доступного terrain, построение или снятие препятствия на тике, встречные группы. Проверить корректность остановки, достижение цели, время разгрузки прохода, столкновения и качество пути, включая случаи с непроходимым маршрутом. |
| **Масштаб** | Для малой встречи начать с десятков акторов. Для общей подмены RTS пройти 100/1000/10000 с несколькими профилями, массовым движением и боем. Снять p50/p95/p99 и максимумы времени тика и кадра, frame publication, CPU/main thread, память и аллокации, число узлов/RIDs и draw calls. Бюджеты тика и кадра зафиксировать до замеров на целевой машине. |
| **Детерминизм** | Для функции, меняющей авторитетное состояние, проверить одни и те же команды с разным pacing, при workers 1/4, повторе, headless и на поддержанных ОС/архитектурах. Проверить восстановление из сохранённого состояния, включая правку карты. Любое расхождение требует объяснения до использования в lockstep. Прохождение тестов подтверждает выбранные версии и сценарии. |
| **Разработка и поставка** | Сосчитать реально удаляемые обязанности. Сравнить импорт, размер релиза/серверного артефакта, cold start, RSS, время CI и удобство отладки. Для Godot headless проверить фактический server preset с теми же семантическими ресурсами. |

**Решение по результату.** Godot следует использовать авторитетно только для заявленного профиля. Для текущего lockstep требуются паритет на поддерживаемой матрице и сохранение игровых инвариантов. Для локального малого режима можно принять другой набор инвариантов, если именно он делает разработку дешевле. Если нативная функция выгодна в редакторе, а authoritative runtime страдает от синхронизации, сохранить её в bake/preview и зафиксировать compiled данные.

## Условия, которые пока задаёт игра-потребитель

- Пиковое число активных акторов, тип карты и необходимые боевые механики.
- Нужны ли сеть, replay и сохранение в середине боя, продолжает ли матч жить при смене экрана.
- Достаточно ли обмена «вход и результат», либо два режима делят пространства, NPC и ресурсы в реальном времени.
- Допустим ли Godot .NET для редактора и экспортных целей всей игры. Какой проект возьмёт на себя первый внешний playtest.

Ответы определяют глубину интеграции. Текущие данные достаточны, чтобы спланировать варианты, и оставляют скорость, стоимость сопровождения и совместимость экспортированной сборки предметом пилота.
