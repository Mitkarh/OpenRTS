# Диагональные тайлы и проходы в OpenRTS

**Основа.** Первоначальные прогоны выполнены на OpenRTS `663ef8a` с реализованным B6 и Godot .NET 4.7.2. Проверены подбор тайлов, их сохранение и движение в малом мире. Действующий формат диагональных обрывов описан в [последнем разделе](#реализованный-срез-диагональный-обрыв).

## Вывод

Godot поддерживает диагональное оформление переходов на квадратном `TileSet` и в изометрии `Diamond Down`. В OpenRTS уже можно пройти по диагонали через целиком проходимый `Z`. Чтобы открытая половина `Z` пропускала юнита, а закрытая останавливала его, потребуется игровая граница внутри клетки. Программный эксперимент с приближением такой границы показал, что текущий движок уже способен двигать тело через этот коридор.

Рекомендуемый первый срез — визуальные переходы с одним `TerrainId`. Следующий срез имеет смысл строить вокруг одного точного разделителя на две половины, если берег, скала или ход по диагональному коридору меняют тактику. Для рамп сначала нужно определить форму и стыки поверхности в игровых координатах.

## Что предоставляет Godot

| Возможность | Как применить |
|---|---|
| Atlas и ручная кисть | Нарисовать варианты `Z` с нужными направлениями диагонали и положить их вручную. Удобно для рамп, где важны конкретное направление и перепад. Можно сохранить группу тайлов как паттерн для повторной укладки |
| Terrain Set | После разметки `Terrain` и Terrain Peering Bits редактор подбирает уже существующие тайлы. `Match Corners` подходит для рисунка по углам, `Match Corners and Sides` учитывает и стыки по сторонам. `Match Sides` годится для связей по краям |
| Terrains → Connect / Path / ручной вариант | Connect подбирает стыки с окружением и может заменить соседние тайлы. Path соединяет элементы текущего штриха. Для сложного перехода можно выбрать конкретный тайл |
| Custom data и полигоны | У каждого atlas-тайла или альтернативы могут быть свои данные и полигоны коллизии, навигации и окклюзии. Для OpenRTS достаточно явных метаданных в первой версии. Полигоны можно рассмотреть как вход компилятора, если фиксированных форм окажется мало |

Правила подбора работают с метками, а контур рисует художник. Набор должен содержать варианты под нужные сочетания, включая внутренние и внешние углы, повороты и пустое пространство там, где его нужно учитывать. Если у нескольких atlas-вариантов одна маска, Godot вправе выбрать подходящий случайным образом. Косметическим вариантам одной формы нужно назначать одинаковые игровые данные, иначе перекраска может изменить матч. [Using TileSets](https://docs.godotengine.org/en/4.7/tutorials/2d/using_tilesets.html#creating-terrain-sets-autotiling) · [Кисти TileMap](https://docs.godotengine.org/en/4.7/tutorials/2d/using_tilemaps.html#handling-tile-connections-automatically-using-terrains) · [TileData](https://docs.godotengine.org/en/4.7/classes/class_tiledata.html) · [Подбор в исходниках Godot](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/scene/2d/tile_map_layer.cpp).

В headless-проверке создал синтетический atlas с X/Y, заполнил X карту 7×7, затем вызвал `set_cells_terrain_connect` для пятна Y размером 2×2 с дополнительной выступающей клеткой. Проверил фактически выбранные atlas-варианты и `TileData` после записи и повторной загрузки `.tscn`. В обеих проекциях `Match Corners` выбрал 4 смешанных тайла в этом сценарии, а `Match Corners and Sides` — 5. Валидные направления peering bits различались. Все 49 клеток сохранились. Эта проверка подтверждает выбор и сериализацию, качество рисунка будет зависеть от реального atlas.

Границу нужно задавать в XY карты. Экранная диагональ в изометрии может соответствовать оси симуляции, а диагональ игровой клетки может выглядеть на экране горизонтальной или вертикальной. Текущий экстрактор восстанавливает базис из `MapToLocal`. Имена сторон и преобразования движения следует привязывать к этому базису. [MapSceneExtractor2D](../../../sandbox/addons/openrts_editor/MapSceneExtractor2D.cs#L80) · [TileMapLayer](https://docs.godotengine.org/en/4.7/classes/class_tilemaplayer.html#class-tilemaplayer-method-map-to-local).

Godot также имеет несколько политик диагонали в `AStarGrid2D`, в том числе игнорирование соседей и требование проходимости обеих боковых клеток. Эти режимы проверяют целые клетки. Половины тайла и габариты конкретного RTS-юнита потребуют дополнительной геометрии. [AStarGrid2D](https://docs.godotengine.org/en/4.7/classes/class_astargrid2d.html#enum-astargrid2d-diagonalmode).

## Как движется юнит в OpenRTS сейчас

1. Экстрактор 2D читает выбранный `TileData` и кладёт в `MapSource` по одному `TerrainId` и `VisualId` на клетку. Для рельефа он также считывает высоту и перепад. Террейны Godot, их peering bits и полигоны в этом пути остаются данными Godot. [MapSceneExtractor2D](../../../sandbox/addons/openrts_editor/MapSceneExtractor2D.cs#L38) · [MapSource](../../../src/OpenRTS.Content/Maps/MapSource.cs#L48).
2. Приказ сначала проверяет точную цель и свободный отрезок. `TerrainGeometry.Clear` проходит клетки отрезка и проверяет, касается ли движущееся тело запрещённых клеток, обрывов или частичных `WorldBox`. Для круга проверяются в том числе округлые углы, для box важны его обе полуоси. При клетке с типом Y правило зависит от локомотора конкретного юнита. [DestinationResolver](../../../src/OpenRTS.Gameplay/Navigation/DestinationResolver.cs#L59) · [TerrainGeometry](../../../src/OpenRTS.Gameplay/Navigation/TerrainGeometry.cs#L8) · [BodyGeometry](../../../src/OpenRTS.Gameplay/Geometry/BodyShape.cs#L21).
3. При необходимости строится обход. Обычный граф и граф точного режима строят связи по четырём направлениям. В точном режиме свободные узлы и рёбра проверяются с телом на сетке 512. Следование может срезать повороты по свободному отрезку. Локальный поиск допускает и диагональные рёбра с полной проверкой тела. Поэтому число направлений глобального графа само по себе не определяет траекторию. [RouteGeometry](../../../src/OpenRTS.Gameplay/Navigation/RouteGeometry.cs#L6) · [LocalMotionSearch](../../../src/OpenRTS.Gameplay/Navigation/LocalMotionSearch.cs#L50) · [Подготовка маршрута](../../../src/OpenRTS.Gameplay/Simulation/SimulationWorld.Locomotion.cs#L36).
4. Для грунта цена маршрута интегрируется по линии движения, скорость берётся из клетки центра в начале тика. Разрешение остановки проверяет область под телом. Разделитель внутри клетки придётся учитывать в каждой из этих операций, если он влияет на соответствующее правило. [TerrainCost](../../../src/OpenRTS.Gameplay/Navigation/TerrainCost.cs#L5) · [TerrainStep](../../../src/OpenRTS.Gameplay/Simulation/SimulationWorld.Locomotion.cs#L25) · [CanStop](../../../src/OpenRTS.Gameplay/Navigation/TerrainGeometry.cs#L63).

## Проверка X2 → X3

```text
X1 | X2
---+---
X3 | Z
```

Прямая между центрами `X2=(1536,512)` и `X3=(512,1536)` проходит через общую вершину `(1024,1024)`. Внутри `Z` у неё нет отрезка ненулевой длины. При этом тело заметает части обоих соседних квадратов у вершины. Чтобы доказать движение **через интерьер Z**, проверял также отрезок от `(1792,768)` до `(768,1792)`. Он входит в `Z` через верхнюю грань и выходит через левую.

Эксперимент использует `NavigationGrid(2,2)`, клетку 1024, `Move` к точной цели и скорость 128 ед./тик. X и проходимый Z имеют одинаковую цену и скорость. Положение центра снималось после каждого тика. Для частичной границы восемь осевых прямоугольников перекрывают юго-восточную половину Z с запасом до 128 по сумме локальных координат. Северо-западная часть остаётся проходом. Препятствия передаются напрямую в `NavigationGrid`, а не через `MapSource`.

| Условие | Наблюдение |
|---|---|
| Проходимый Z, X1 открыт | Смещённые точки соединены прямой через Z за 12 тиков, центр не заходил в X1 |
| Z целиком запрещён локомотором, X1 открыт | Из центра X2 юнит дошёл до центра X3 через X1 за 22 тика |
| Z проходим, X1 закрыт | Диагональ между смещёнными точками по-прежнему заняла 12 тиков |
| Часть Z закрыта прямоугольниками, X1 закрыт | По прямой между смещёнными точками прошли круг радиуса 128 и box 128×128 по полуосям. Оба за 12 тиков |
| Те же препятствия, приказ между центрами | Круг радиуса 128 немного повернул, зашёл в свободную часть Z и дошёл до X3 за 14 тиков |
| Те же препятствия, круг радиуса 400 | Проверка достижимости признала X3 недоступным |
| Z и X1 целиком закрыты | Проверка достижимости отвергла щель из одной вершины для конечного тела |

Проход через половину Z подтверждён для малой карты и конкретных тел. При одинаковой цене сократить путь через Z возможно. Если цена в Z выше, обход через X1 может стать предпочтительным. Для узкого прохода важно проверить и геометрию, и поиск. Физически допустимая траектория может не найтись, если в свободной части отсутствуют доступные узлы или привязки. Пример с прямоугольниками показывает возможность переиспользовать текущую проверку тел. Испытания точных диагональных полигонов потребуют отдельного прототипа.

## Варианты игровых данных

| Подход | Что получает игрок | Цена и ограничение |
|---|---|---|
| **Один тип, диагональный рисунок** | Плавный стык травы и грунта, дороги и обочины. Через Z можно идти под углом, если назначенный тип проходим | Текущих `TerrainId` и `VisualId` достаточно. При непроходимой стороне рисунок может заметно расходиться с краем проходимости |
| **Один отдельный тип перехода** | Например, целый тайл мелководья или мокрого грунта. Пехота замедляется, лодка или тяжёлая машина получает своё правило | Достаточно обычного terrain и правил локомоторов. Вода и суша в одном тайле остаются одной игровой областью, зато можно задать собственную цену и остановку |
| **Подразбиение или осевые препятствия** | Приближение берега и прохода с точными позициями движения | Свободное место зависит от разрешения. У глобальной сетки 2×2 на каждый тайл в четыре раза больше samples; это не то же, что добавить четыре локальных элемента только в Z. Текущий map compiler и формат потребуется расширить для авторинга такого слоя |
| **Точная граница на две части** | Юнит проходит по X-половине, а проходимость и цена Y зависят от локомотора. Форма прохода соответствует выбранному тайлу | Понадобятся детерминированные swept-проверки и цена пересечения, правила остановки, узлы или входы в узкий проход, а также визуализация границы |

Для точного варианта предлагаю начать с двух возможных диагоналей квадрата и назначения X/Y по сторонам. Две выпуклые половины занимают одну XY-клетку. Сохранять имеет смысл ориентацию и типы в редкой секции переходов. Для круга проверяется зазор до ребра и его концов, для box — попадание отрезка движения в многоугольник, расширенный полуосями тела. Границы сравниваются в целых координатах или рациональных дробях, включая единое правило касания. Непроходимость проверяется для всего тела, а цена и скорость читаются по положению его центра. Для цены нужно делить отрезок по пересечению с разделителем. Для первого среза остановка требует допустимой опоры под всем телом, как на действующих границах terrain. Это позволяет отдельно настроить мелководье, лёд и скалу. [Действующие правила locomotor](../../../src/OpenRTS.Gameplay/Navigation/Locomotor.cs#L7) · [Частичная геометрия и навигация](../navigation-layers/geometry-and-micro.md).

Разрешение перемещения между двумя выходами клетки можно использовать как производное ускорение. Само по себе оно не обеспечивает зазор под тело. Начните с действующих прямых отрезков и сетки 512. Если свободные коридоры теряются между её узлами, проверьте узлы или порталы вдоль границы только у переходных клеток. Вариант с общим navmesh или делегированием Godot имеет смысл при более широком наборе геометрии и отдельной проверке детерминизма. [План навигационного compiler](../map-compilation/navigation.md).

## Диагональные рампы

Уклон внутренней поверхности и линия границы между материалами — независимые параметры. Первоначальный пилот v3 принимал перепад только по одной оси. Текущий v3 поддерживает оба компонента `Rise`. В прямом тесте `NavigationGrid` вычислил высоты углов **256, 512, 512, 768** для `Elevation=512, Rise=(256,256)`. На момент первоначального теста компилятор ещё отклонял этот параметр в `MapSource`. [NavigationGrid.SurfaceElevationAt](../../../src/OpenRTS.Core/Navigation/NavigationGrid.cs#L123) · [MapCompiler](../../../src/OpenRTS.Content/Maps/MapCompiler.cs#L61) · [Формат v3](../../decisions/047-map-compilation.md#версия-3--одна-поверхность).

Есть два осмысленных расширения.

1. **Одна наклонная плоскость в клетке.** Подходит для полосы из взаимно согласованных диагонально наклонённых клеток. При значениях `(256,256)` максимальный градиент равен `256√2` единицам на размер клетки. В действующем контракте `MaximumSlope` сравнивается с длиной вектора перепадов, округлённой вверх. Осевые рампы сохраняют прежние значения. [MapSurfaceCell](../../../src/OpenRTS.Content/Maps/MapSource.cs#L29).
2. **Плоская и наклонная части внутри пограничной клетки.** Это нужно, когда наклонная плоскость встречает площадку по диагональной линии уровня. Весь бок клетки обычно нельзя совместить с плоской площадкой, если высота изменяется вдоль него. Для типовой формы подойдёт разделённая клетка с высотами вершин и двумя плоскими фасетками. Для полосы подъёма можно описать общую наклонную плоскость, ограниченную снизу и сверху высотами площадок, и извлечь её части при компиляции. У непрерывной рампы высоты совпадают вдоль общих рёбер. У скалы по тем же XY-рёбрам разрешён перепад с проверкой `MaximumStep` и тела. Текущая проверка клипует осевое ребро по порогу `MaximumStep`. Внутриклеточный обрыв добавляет отдельное диагональное ребро. [TouchesCliff](../../../src/OpenRTS.Gameplay/Navigation/TerrainGeometry.cs#L49) · [TerrainSurface](../../../src/OpenRTS.Godot/Rendering/TerrainSurface.cs#L14).

Высоту объекта, точку клика и рендер поверхности следует вычислять из одной геометрии. Иначе для одинакового XY редактор, симуляция и видимый склон могут дать разные места остановки. Стороны диагонального обрыва имеют разные высоты в своих областях XY. Многослойность нужна отдельно, когда доступны разные поверхности над одним и тем же XY внутри области, например мост и дорога под ним. [Исследование 3D-рельефа](../3d-terrain/README.md).

## Предлагаемая проверка перед реализацией

1. Один комплект диагональных переходов для травы и грунта в штатном atlas, включая ручной вариант и обе проекции. Один и тот же игровой ID у визуальных вариантов. В текущем compiled sandbox привязка `VisualId` к текстуре задаётся отдельно от atlas исходной 2D-сцены. После перекраски сравнить игровой отпечаток. [Загрузка текстур в Sandbox](../../../sandbox/Sandbox.cs#L259) · [Отпечатки и B6](../../decisions/052-map-match-replays.md).
2. Если нужен игровой берег или скала, взять один Z с разделителем, два направления диагонали и обе стороны X/Y. Повторить пример с запрещённым X1, кругом и box, добавить широкое тело, остановку в X/у границы, группы и изменение блокировки footprint. Проверять координаты траектории, а не только факт прибытия.
3. Отдельно испытать диагональную рампу между площадками с подъёмом и спуском, включая точный порог slope/step и стык на середине ребра. Сверять высоты от compiler до рендера, позиции стартов и seed/hash в headless и Godot.
4. Для игровых переходов новая семантика входит в `GameplayFingerprint` и состояние симуляции, оформление следует прежней политике `DataFingerprint`. Старые M1/v1–v3 сохраняют прежний смысл. До перехода на большие карты измерить загрузку, первый путь, плотную группу и стоимость подготовки узлов на карте с редкими и частыми Z. [Контракт компиляции](../../decisions/047-map-compilation.md) · [Измерения навигационной подготовки](../map-compilation/navigation.md).

## Реализованный срез. Диагональный обрыв

Для отвесной стенки нужны две высоты и физический разделитель. Вариант с одним новым `TerrainId` снова описывал бы всю клетку, а мелкая сетка дала бы ступенчатую границу и увеличила число навигационных узлов. Поэтому разрез хранится как свойство поверхности в [формате v4](../../decisions/047-map-compilation.md#версия-4--диагональные-обрывы), а одинаковый тип грунта определяет движение по обеим половинам.

1. Автор выбирает один из четырёх явных атласных тайлов Godot. Custom data хранит высоты и верхний угол. Повороты атласа не преобразуют поля высоты. Подбор тайла по peering bits зависит от соседей, здесь направление задаёт автор. [Метаданные TileSet](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html#assigning-custom-metadata-to-the-tileset-s-tiles).
2. Компилятор переносит числа в независимый артефакт. Симуляция вычисляет сторону по целым локальным XY и использует высоту центра юнита для позы. Когда перепад больше `MaximumStep`, движение сравнивает весь след тела с отрезком диагонали. Для круга проверяется пересечение и ближайшая пара точек двух отрезков. Для прямоугольника проекции сравниваются по осям клетки и по нормалям к стенке и направлению движения. Касание блокирует. Стыки с соседними клетками берут высоту половины, которой принадлежит общая грань.
3. Godot строит два горизонтальных треугольника и стенку из тех же данных. Луч клика по треугольнику даёт точный XY на соответствующей высоте. Удар луча о стенку означает отсутствие наземной цели.
4. Карта `DiagonalCliffs` покрывает все четыре ориентации. Проверки проходят через TileMapLayer, исходный JSON и compiled JSON, сверяют выбор обеих высот и попадание в стенку, затем проводят одного бойца вокруг плато, другого по верхней половине и сравнивают состояние при повторе с другим числом работников. Отдельная проверка замыкает две половины одной клетки для круга и прямоугольника и проверяет прохождение при достаточном `MaximumStep`.

Это срез наземного движения и размещения по опорной высоте. Наклонные треугольники, проверка высоты опоры под всем footprint здания, баллистическая дуга и экранирование обзора для тумана войны остаются самостоятельными задачами. Для прямого пространственного выстрела разрез уже участвует в [линии огня и столкновении снарядов](../../decisions/011-weapons-and-projectiles.md#траектория-и-диагональные-обрывы). Маршруты используют текущую решётку 512. Точный swept-тест проверяет найденный отрезок, а достижимость узких лазов по-прежнему зависит от доступных узлов. Замеров на больших картах с плотными разрезами пока нет.

Раздельный грунт реализован в [v5](../../decisions/047-map-compilation.md#версия-5--раздельный-грунт). Этот формат также покрывает ровный диагональный берег. Проходимость и остановка используют оба треугольника, скорость читает грунт под центром, а стоимость маршрута делит сегмент по диагонали.
