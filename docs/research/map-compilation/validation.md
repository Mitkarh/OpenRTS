# Проверки, метрики и критерии выигрыша

[Обзор](README.md) · [План MC0–MC9](plan.md). **Статус:** протокол будущих экспериментов. В этой работе измерения и игровые прогоны не выполнялись.

## Не смешивать три вида результата

1. **Корректность:** совпадает ли подготовка с исходными правилами, нет ли ложных проходов/площадок, соблюдается ли детерминизм и знание игрока.
2. **Вычислительная стоимость:** сколько стоит подготовить, загрузить, обновить, найти маршрут или принять решение.
3. **Качество игры:** куда реально доехали, что построили, сколько доставили и потеряли.

Уменьшение CPU при застрявших юнитах или плохой экономике не считается успехом. Перенос работы из тика в загрузку показывается как перенос, а не исчезновение затрат.

## Сравниваемые варианты

| Вариант | Назначение сравнения |
| --- | --- |
| A. Нынешнее ленивое построение | Текущий baseline |
| B. Та же подготовка до первого тика, без файла | Отделить стоимость холодной инициализации от исполнения |
| C. Загрузка того же результата из файла | Отделить экономию повторного построения от B |
| D. Один уровень иерархии + прежний подробный поиск | Выигрыш новых дальних запросов относительно B/C |
| E. D с локальными обновлениями | Цена изменений относительно полной корректной пересборки D |
| F. Подготовленные точки/площадки ИИ | Сравнить с нынешними кольцами/эвристиками при одинаковых остальных правилах |

Отдельно отключать семантические признаки и runtime-оценку, чтобы различить пользу площадок, маршрутного расстояния и новой политики ИИ. Один эксперимент не должен одновременно менять карту, баланс армии, навигацию и стратегию.

## Набор карт и сценариев

Использовать штатные [карты](../../../sandbox/content/maps) с перестановкой стартов плюс небольшие диагностические и процедурные нагрузки. Нельзя обучить/настроить эвристику на одном сценарии и считать весь набор независимой проверкой; часть карт отложить для итогового сравнения.

| Сценарий | Что различает |
| --- | --- |
| Открытое поле, близкий/дальний приказ | Накладные расходы подготовки и сохранение прямого fast path |
| Длинная стена, озеро, лабиринт | Реальная польза глобального поиска, в том числе при близких координатах |
| Несвязные области внутри одного сектора | Ложную достижимость coarse-графа |
| Узкие/частичные проходы, несколько тел и sampling | Соответствие profile/clearance и пределы подробной решётки |
| Болото с быстрым объездом, transit-only участок | Стоимость маршрута и CanStop, недопустимость одного усреднённого веса |
| Много разных дальних целей и одна большая группа | Новые поля против разделяемого коридора/дерева |
| Здание внутри сектора и на его границе | Внутреннее разделение, запас для тела и зависимости соседей |
| Стена через несколько секторов, пачка стройки/разрушения | Глобальные последствия и очередь обновлений |
| Перекрывающиеся stamps, удаление в разном packed-порядке | Сохранение порядка композиции по domain ID |
| Истощение блокирующего источника | Открытие пути без изменения базового terrain |
| Два близких ресурса по разные стороны утёса | Географическую кластеризацию против Euclidean clustering |
| Одиночный ресурс, остров, узкий подъезд к станции | Непереносимость StarCraft-предположений и доступность обслуживания |
| Несколько площадок центра, встречный транспорт | Доход против кратчайшего расстояния, очереди и выходы |
| Два планировщика выбирают один район | Резервирование и отсутствие дублирующего расширения |
| Два направления с общим мостом; обход без общей горловины | Реальную независимость вариантов захода |
| Смена стартов, фронта, атакуемой базы | Относительность тыла и приоритета обороны |
| Прорыв: ещё один блокировщик, отмена, смерть исполнителя | Условную связь и подтверждение результата действия |
| Одинаковые наблюдения, разные скрытые запасы/враги | Отсутствие утечки через атлас и оценку |
| Эквивалентные YAML и Godot-входы | Один источник правил преобразования |

Нагрузки на 10000 объектов выполнять там, где они проверяют заявленную цель. Число entities не заменяет размер карты, число профилей, новых целей и изменений. Малые exhaustive/oracle-карты нужны даже при хорошем большом benchmark.

## Метрики подготовки и загрузки

| Метрика | Определение / единицы |
| --- | --- |
| `extract_ms`, `normalize_ms`, `validate_ms` | Извлечение из источника, преобразование и проверка по отдельности |
| `geometry_build_ms`, `components_build_ms`, `hierarchy_build_ms` | Структуры по профилям; не включать их скрыто в одну «загрузку» |
| `ai_atlas_build_ms`, `presentation_build_ms` | Дополнительные секции отдельно |
| `read_ms`, `decompress_ms`, `verify_ms`, `write_ms` | Полный путь файла, включая проверку актуальности |
| `ready_ms` | От начала загрузки до согласованного мира, готового принять первый приказ |
| Размер | Байты источника, файла/секций, resident и peak memory, bytes/node/profile/candidate |
| Переиспользование | Число принятых/перестроенных секций, причина отказа, доля повторно используемых данных |
| Инкрементальная подготовка | Время правки одной декорации, коллизии, профиля, роли/footprint и полной пересборки |

Различать холодный/тёплый файловый кэш ОС, отсутствие подготовленного артефакта и уже подготовленный runtime. Если холодное чтение ОС не контролировалось, так и обозначать результат.

Для повторного использования `B` — время построения, `L` — чтение+проверка. Экономия на повторном запуске равна `B−L`. При отдельной однократной сборке стоимость `B + K×L` меньше `K×B`, когда `K×(B−L)>B`; учитывать размер распространения и память отдельно. Это модель времени, не обещание измеренного выигрыша.

## Навигация и изменения

Измерять `request_cpu_ms`, раскрытые узлы/рёбра, профиль/тип запроса, cache hit/miss, число подробных уточнений, длину коридора, число fallback и причину. **Задержка готовности** — тики и реальное время от принятия приказа до пригодного участка; низкое время CPU одного тика не оправдывает бесконечный pending.

Для изменений: время композиции геометрии, число dirty/rebuilt секторов/порталов, пересмотренных маршрутов и агентов; время обновления глобальной связности; длина/возраст очереди работ; время до готовой новой ревизии. Сравнивать с полным rebuild при том же изменении и состоянии. Не скрывать массовый проход по агентам после сокращения пересчёта графа.

Стоимость пути сравнивать с oracle на том же подробном графе: `cost_ratio = candidate_cost / oracle_cost` для положительной эталонной стоимости. Случай совпадающих точек и недостижимость учитывать отдельно. Это не отношение к неизвестному непрерывному оптимуму. Длина, route cost, фактические тики поездки и влияние очередей — отдельные величины.

Дополнительно: доля завершённых приказов к горизонту, время прибытия p50/p95/max, время без продвижения, число локальных перепланирований/уступаний и пропускная способность узких мест. Плотная толпа, прямые независимые ряды и бой — разные профили.

Нынешний `WeightedNavigator.Milliseconds` замеряет построение полей после `Geometry.Prepare`. Компоненты и часть вызовов находятся вне этого интервала. Расширение измерений должно закрыть эти пропуски до выводов о холодной цене. [S001](sources.md#s001).

## Метрики ИИ

| Решение | Стоимость вычислений | Проверка качества |
| --- | --- | --- |
| Площадка здания | Кандидаты и geometry/reachability queries на успешную стройку, CPU и циклы планирования | Принятые/завершённые стройки, время ожидания, доступ строителя, свободные выходы |
| Ресурс/расширение | Число рассмотренных точек, время shortlist/ranking, cache reuse | Дополнительные доставленные кредиты, окупаемость, простой машин, потери и незавершённые базы |
| Оборона | Проверенные проходы/позиции, время оценки, число переключений | Ущерб защищаемым активам, потери/цена гарнизона, сохранение своей логистики, доступность обхода |
| Разведка | Число кандидатов и запросов покрытия | Новые полезные наблюдения за время/стоимость, время обнаружения расширения, потери разведчиков |
| Обход/прорыв | Число коридоров, время поиска/оценки операции | Реальное различие входов, прибытие, потери, время и стоимость открытия, отмены |

Записывать объяснение выбора и отказов: ID района/кандидата, наблюдаемость, жёсткое ограничение, основные признаки, дата данных. Это помогает различить ошибку геометрии, устаревание, неверную оценку и неспособность исполнить хороший план.

Для силы ИИ нужны парные матчи с теми же картами/seed, перестановкой сторон и неизменными оппонентами. Win rate и длительность матча дополняют экономические/тактические метрики; маленькая выборка не доказывает превосходства. Для первых MC3/MC6 достаточно целевых сценариев с воспроизводимым результатом; массовый турнир не является обязательным условием проверки площадок.

## Проверки корректности

- Исходный и подготовленный входы, а также rebuild и load одного алгоритма дают одинаковые игровые данные и состояние при одинаковом журнале. Сравнение хешей со старым алгоритмом требуется для прозрачной подготовки MC1/MC2; смена маршрутизации MC4 оценивается отдельно и не обязана сохранять старый маршрут.
- Для фиксированного backend 1/4 workers, reverse jobs и повторная сборка дают одинаковые результаты. Из равных вариантов выбирается устойчивый ID/порядок; имена файлов и порядок Dictionary/archetypes не определяют решения.
- Малые графы сверяются с независимым подробным поиском. Для готовых переходов нет ложных разрешений, для известных достижимых пар относительно reference нет необъяснённых отказов. Ограниченный shortlist не выдаёт себя за полный поиск.
- Эффективный граф после каждой последовательности изменений сравнивается с полным rebuild. Генерировать случаи на границах секторов, разных телах, нескольких stamps и разных последовательностях Spawn/Delete. Проверять как открытие, так и закрытие пути.
- Переключение изображений не меняет игровые секции; изменение геометрии/физического профиля инвалидирует нужные результаты. Начальный порядок placements и привязка authoring/runtime IDs сохраняются при смене стартового набора.
- Отсутствующий, устаревший, обрезанный или неверный кэш даёт rebuild/явную ошибку, а не частичный мир. Проверяются отмена, Dispose, одновременная попытка публикации файла и повторное открытие готового результата.
- Для знания ИИ использовать пару миров с одинаковыми разрешёнными наблюдениями и публичными метаданными, но разными скрытыми фактами. До их наблюдения/разрешённого взаимодействия решения не должны отличаться. Публичность геометрии задаётся режимом; тест не скрывает данные, объявленные публичными. Отдельно проверить отсутствие чтения скрытого через площадки/полные world queries.
- Условный проход не считается открытым до события и проверки геометрии. Скрытая преграда не выдаётся ИИ как известный объект из технической секции.

## Метод измерения и критерии продолжения

Для будущего отчёта фиксировать commit/локальные изменения, отпечатки карты/каталогов/артефактов, настройки и policy version, оборудование, ОС, .NET, Release/JIT, workers, команду, seed и игровой горизонт. Хэш, публикацию кадров, AI planning и renderer измерять раздельно от `World.Step`, затем показать полную стоимость реального хоста. Аллокации вызывающего потока не выдавать за все потоки; дополнительно учитывать процесс, retained/peak memory и GC.

Рекомендуемый минимальный старт — несколько независимых повторов каждого варианта с чередованием порядка; число повторов увеличить при заметном шуме. Прогрев JIT выполнять отдельно и описывать. Не оценивать p99 по нескольким наблюдениям: показывать объём выборки, полное распределение/максимум и интервалы неопределённости там, где они оправданы.

Показывать первый тик и тики изменений отдельно **и** в полной статистике. Не удалять пики из общего отчёта ради красивого p95. Повторные warm-запросы не заменяют холодные. Исторические [N1](../../verification/010-terrain-locomotors.md) и [N2](../../verification/013-buildings-and-geometry.md) сохраняются как мотивация; их числа не становятся новым baseline.

До реализации после MC0 определить бюджеты времени загрузки, памяти, задержки маршрута, дополнительного CPU ИИ и допустимого удорожания пути. Для 25 Гц весь тик располагает 40 мс; это не отдельные 40 мс навигации плюс 40 мс ИИ. Бюджет самого ИИ согласуется с реальным host scheduling.

**Продолжать этап**, если корректность выдержана, улучшена целевая метрика сверх разброса повторов, а загрузка/память/качество/задержка остаются в заранее выбранных бюджетах. **Остановиться на простой версии**, если переноса подготовки в загрузку достаточно, файл не экономит время, иерархия не окупается или атлас ухудшает решения. Численный процент ускорения и обещание масштаба до выполнения этих сравнений не задаются как доказанный результат.
