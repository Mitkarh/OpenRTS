# 039. NET2 WAN: bounded pipeline и периодические checkpoints

**Дата:** 16 ноября 2026. **Статус:** реализовано и проверено в профилях [039](../verification/039-net2-wan.md). Заменяет строгий batch/hash barrier из [038](038-net2-live-direct-matches.md); основной режим по-прежнему прямой клиентский lockstep. Доверенный игровой сервер не добавлен.

## Pipeline

`PeerPipeline` — один async reader и один async writer над TCP/SslStream с bounded channels по32frames. Каждый frame≤256KiB; максимум очередей16MiB payload на peer плюс bounded tick/history state и системные TCP-буферы. I/O задачи не получают SimulationWorld или ECS refs. Декодирование, изменение inbox/checkpoint state, Step, journal и публикация остаются на owner thread. Pending maps ограничены игровым окном, не длительностью матча.

Hello/Ready остаются стартовым барьером. После него owner закрывает batch `n+D` и ставит его в send queue, не ожидая ни отправки в socket, ни ответа на этот будущий batch. Тики1..D−1 согласованно пустые; для следующего реального тика ждём только соответствующий remote batch. Чтение/отправка продолжаются во время Step и pacing. Так D действительно перекрывает задержку доставки, а не добавляется поверх синхронного обмена на каждом тике.

Порядок команд — issuer/sequence, как раньше. Одинаковые sealed batches идемпотентны в пределах recent history, конфликтующие/просроченные/чужие и sequence gaps фатальны. Каноническая упаковка player intents и игровые хеши не менялись. Peer может опережать другого на часть окна; допустимое окно входящих batch/hash ограничено `W=2D+H`, где H — HashInterval. Missing input не заменяется пустым batch.

Pacing использует монотонные сроки фиксированного периода. Мелкий oversleep не накапливает систематический дрейф. При долгой остановке долг сбрасывается: допускается не более одного catch-up тика, без неограниченного fast-forward. Wall-clock влияет на расписание, но не на численную длительность игрового тика/порядок результатов.

## Проверка состояния

HashInterval согласуется в descriptor, диапазон1..64, default8. Каждый H-й тик отправляет checkpoint асинхронно. Owner сравнивает последовательные checkpoints, когда есть оба hash, и ограничивает продвижение относительно последнего проверенного тика: при `Tick−VerifiedTick>=W` ждёт проверку. Пропуск checkpoint, конфликт/слишком далёкий tick или несовпадение — ошибка. Поток только команд без hashes не может поддерживать бесконечное непроверенное исполнение.

Графические кадры теперь могут относиться к ещё не проверенным удалённым hash тикам. На расхождении дальнейшее исполнение/публикация прекращаются, DesyncException указывает первый несовпавший **проверенный** checkpoint. Каждый завершённый тик по-прежнему записывает локальный Report/hash в journal: файлы позволяют отдельно искать первый локальный расходящийся тик при replay/сравнении. Поэтому экономия сети не означает отмены стоимости полного локального Report; профиль10000объектов и его hash cost здесь не измерялись.

## Backpressure и отказы

Зависший writer ограничен deadline одного frame, а enqueue/flush — собственной общей deadline. Owner ожидает конкретное продвижение с фиксированным бюджетом времени; дубли и уже заполненный receive channel не продлевают его. Переполнение канала тормозит producer, не создаёт неограниченный backlog. Отключение/ошибка I/O передаются owner с исходной причиной. Cancel/Dispose закрывает stream и останавливает обе I/O задачи; мир освобождается owner. Частичный Step не публикуется по прежнему контракту.

Медленный расчёт клиента замедляет согласованное продвижение остальных через нехватку требуемых batches. После восстановления журнал/хеши сходятся; тики и команды не пропускаются. Бесконечно остановившийся клиент приводит к timeout, а не локальному исключению участника/самовольному продолжению.

## Завершение

Leave объявляет будущую границу `T=Tick+D`. Объявление ставится в поток перед последним необходимым batch. При одновременных предложениях берётся меньшая граница; TCP order и необходимость batch T не позволяют корректному peer перескочить её. Будущие уже закрытые команды за T не исполняются.

Оба owner доигрывают T, обмениваются terminal hash и финальным ACK. Все периодические checkpoints до T обязательны. ACK физически flush-ится до закрытия stream; read-side EOF, пришедший после получения ACK другим peer, не прерывает уже идущий успешный flush; buffered финальные frames читаются до EOF, но не после истечения deadline. Success journal/footer и Completion появляются только после согласованного завершения и закрытия файла. Это не механика победы/поражения, reconnect или host migration.

## Версии, диагностика и UI

Wire major3 / journal format3, несовместимы с версиями1/2. Descriptor содержит HashInterval; D1..16 выбирается при создании матча и должен совпадать. В Godot появился «Буфер ввода · тики», default6. Больше D — больше допустимой задержки, но более позднее применение намерения; автоматической смены D в матче нет.

`NetworkTickSample`/`DirectSession.Statistics` содержат tick/verified tick, время ожидания необходимых команд/проверки, sealed→Step-end latency, elapsed simulation time и high-water marks очередей. Это локальные метрики, не игровые данные и не часть hash. Sealed latency включает пустые batches и не включает UI queue до collect; submit→published-frame измеряется отдельно в WAN peer harness и не называется GPU/display latency.

## Проверка транспорта

`verify-wan` — bounded TCP relay с seeded jitter, periodic segment loss/retransmission/HOL model и bandwidth cap; прикладные байты не удаляются. `verify-wan --netem` — настоящие потери Linux kernel на eth0 одноразового контейнера, два отдельных .NET peer-процесса и TLS end-to-end через relay. Оба источника нужны: модель даёт устойчивые граничные сценарии, kernel test подтверждает восстановление настоящей TCP-доставки.

Контейнер имеет только NET_ADMIN в собственном network namespace; правила macOS/host networking не меняются. iproute2/Go/Debian/Python — test-only инструменты контейнера с сохранёнными в образе уведомлениями, не зависимости MIT runtime. После теста контейнер удаляется. Relay разбивает путь на два TCP-leg, поэтому эти результаты не являются benchmark end-to-end TCP congestion control единственного соединения через публичный интернет.

NET2 завершён в указанном проверенном профиле. Нельзя обещать25Гц/фиксированную latency при произвольных потерях, CPU, размере мира, маршруте или пропускной способности. Следующий функциональный этап — NET3 (несколько игроков/membership); защищённый режим остаётся последней optional возможностью NET8/NET9.
