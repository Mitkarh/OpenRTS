# 042. NET4.1: журнал исходного матча, проигрыватель и replay recovery

Уточнение17ноября после аудита: default cap поднят до1млн тиков при прежних64MiB/15с; [контракт045](045-network-audit-hardening.md), [проверки045](../verification/045-network-audit.md).

**Дата:** 17 ноября 2026. **Статус:** реализован первый срез NET4; [проверки](../verification/042-net4.md). [План NET4](../research/networking/net4.md). Canonical runtime snapshot, reconnect и NET4 целиком остаются незавершёнными.

## Выбор первого среза

В текущей симуляции есть запись состояния для Report/hash, но нет readers. Состояние распределено между allocator/RNG, ECS-компонентами и механиками Gameplay, навигацией и сенсорами. Сериализация Frent handles, FrameLease или только поз не восстанавливает игровой мир.

Используется предусмотренная roadmap промежуточная ветка: tick-zero фабрика + полная записанная история. Восстановление K стоит O(K), а не O(runtime state). Артефакт называется ReplayCheckpoint; это сохранённый префикс команд, не быстрый snapshot. Он возвращает живой SimulationWorld для продолжения теми же последующими командами. Policy ИИ, соединения, tokens/epochs и пользовательский ввод вне World этим не восстанавливаются.

## Журнал v3

Новый StarJournal записывает полный MatchDescriptor, начальный World hash, game-owned recipe≤16KiB и начальный MatchState, затем прежние control/Turn/batches/Hash/Finish/Complete. У sandbox recipe содержит map/start-set ID, fog, D, tick rate, slots/starts/teams, **SpeedPerTick и FogHoldTicks**. Последние два параметра раньше зависели от локального manifest/CLI; теперь Host передаёт их клиентам, а replay не берёт их из текущих настроек запуска. Правила нового sandbox bootstrap — openrts-lobby-v3. Фабрика повторов также принимает v2 для стандартных старых recipe с defaults128/0; отсутствующие нестандартные параметры из старой записи восстановить автоматически нельзя.

StarJournalReader — общий структурный parser для Replay, Inspect, checkpoint и owner playback. Он проверяет размеры, версии, descriptor, UTF-8, начальную готовность, Match/Player/Tick, contiguous command sequences, control revisions и обязательный финальный hash/footer без trailing data. ReadInfo читает только пролог: это не доказательство завершённости файла. Inspect проходит весь поток и проверяет структуру; смысл World hashes проверяется при применении команд.

StarJournal.Replay для v2 сохранён при явно переданных descriptor и фабрике. V2 не содержал recipe и полного descriptor, поэтому браузер не обещает его автоматического открытия. MatchJournal v3 диагностических двухсторонних матчей не менялся. Существующие файлы не переписываются.

## ReplayCheckpoint

Capture принимает завершённый seekable журнал, проверяет структуру, копирует пролог и префикс до K, завершает его terminal hash/Complete. Контейнер: magic ORTS-RCP, version1, tick K, длина, SHA-256 payload, payload-журнал. Digest проверяет целостность, не удостоверяет результат матча и не является подписью.

Restore ограничивает размер, проверяет версию/длину/digest/trailing bytes, создаёт tick-zero World через фабрику, включает ownership policy, сравнивает initial hash и применяет историю с проверкой **каждого** World hash. Граница payload должна совпасть с K. При успехе RecoveredReplay отдаёт мир вызывающему owner thread; caller владеет Dispose. Ошибка/отмена/timeout освобождает мир, частичный мир не возвращается.

ReplayLimits: по умолчанию≤64MiB и1000000тиков; можно задать более строгие пределы, верхний tick cap1млн. Catch-up timeout по умолчанию15с (верхний предел1мин). Отмена передаётся в Step; фабрика и синхронные стадии проверяются между операциями. Это не обещание прервать произвольный пользовательский callback посреди его исполнения. Размеры сжатых данных не нужны: сжатия в этом формате нет.

## Owner playback и UI

ReplaySession владеет миром на отдельном потоке. Он предварительно проверяет структуру файла, создаёт исходный мир и публикует tick0 на паузе. Доступны Play/Pause, StepOnce, скорость0.125..8× и Seek. В конце файл полностью проверяется, playback остаётся на паузе и допускает seek; Completion означает завершение owner, а не достижение последнего тика.

Seek пересоздаёт мир, применяет команды0..K без промежуточной публикации/исторических VFX events, проверяет hashes и только затем публикует целевой frame. Очередь seek хранит последнюю ещё не принятую цель. Перенос ECS refs через ожидания отсутствует. Слоты кадров закрепляются обычным FrameLease; отмена освобождает owner даже при закреплённых читателями кадрах. Накопление событий ограничено65536.

Главное меню → «Повторы» показывает до100новейших .journal из user://network. Нет неподдержанного контента/recipe — нет запуска. Загрузка требует установленной карты/правил/контента; журнал не поставляет код или ресурсы. После загрузки панель позволяет шаг, скорость, переход по тику и POV «весь мир / игрок». Ввод команд заблокирован в bridge, RTS controls и горячих клавишах. Ошибка загрузки остаётся в браузере, runtime failure даёт возврат в главное меню.

После seek/POV reset очищаются выбор, placement modes, wrecks/VFX/radar caches и временное удержание графического тумана, чтобы состояние предыдущего момента не оставалось в новом. Игровые fog/knowledge берутся из восстановленного мира. Replay полностью раскрывает исходный lockstep-мир; к безопасному режиму это не относится.

## Границы доказательства

Production100, aviation420 и sensors48 проверены восстановлением на0/K/T и совпадением каждого дальнейшего hash при тех же командах; restart проверен отдельным процессом. Это проверка replay recovery небольших сценариев, не полный аудит всех механик/сохранений и не benchmark10000объектов. RNG seed входит в исходное состояние; изменяющий RNG Scatter не является разрешённым сетевым intent и в этой матрице не используется.

Следующий этап NET4.2 должен дать настоящие схемы runtime snapshot, включая зарегистрированные механики и внешнюю AI policy либо явный согласованный reset. Затем NET4.3 — resume credentials/epochs, chunked transfer, bounded catch-up и включение в barrier. Mid-game join/rejoin, два одновременных rejoin и host migration сейчас не реализованы. Trusted authoritative mode остаётся последним дополнительным NET8/NET9.
