# 046. Остаток аудита NET1–NET5: каталог, вместимость и диагностика

**Дата:** 17ноября2026. Пункты5–8 после [исправлений045](045-network-audit-hardening.md). [План](../research/networking/roadmap.md), [проверки046](../verification/046-network-directory-diagnostics.md).

## Confirm вне барьера матча

`reservation_missing` — окончательный ответ для одного receipt: он удаляется из очереди, следующие подтверждения продолжаются. Временные HTTP/network ошибки сохраняют головной элемент для повтора; `lease_invalid`/`match_expired` по-прежнему запускают повторную публикацию. Очередь DirectoryListing и входящая очередь admission в StarSession ограничены1024элементами каждая. Поведение отменённого offline capability не меняется: Cancel не отзывает уже выданный ticket у хоста.

Проверка реальным HTTP/TLS сценарием: Confirm503 → повтор того же receipt →404 отменённой резервации → успешный следующий receipt. Пока публикация повторяет запрос, тики игроков продолжаются. Стандартный HttpMessageHandler используется для инъекции ответа503 и подмены тестового grant; производственный клиент сохраняет прежний запрет redirects и5с deadline.

## Полное число сторон до handshake

`MatchAdvertisement.PlayerCount` — число всех мест, включая AI и закрытые; `Players` — подключённые human. Capacity2..8 фиксирована на время регистрации и подписана в ticket v2, возвращается в MatchJoinGrant. Сервис проверяет диапазон свободных мест, connected+available≤capacity и запрещает менять capacity через heartbeat. Клиент сверяет grant с подписанными claims; host проверяет capacity в proof и при одноразовом Redeem.

StarSession при новом catalogue admission берёт число мест из grant, а не из default playerCount=2. Для прямого входа и NET4 resume остаётся явный playerCount; sandbox использует четыре места. В библиотеке проверены2/4/8мест с human/AI/closed и spectator; Godot browser явно блокирует вход и просмотр записей с иной вместимостью и объясняет ограничение. Это не расширение MatchSetupOptions на восемь мест.

## RTT и Waiting

StarProtocol5 добавляет Ping/Pong с положительным nonce и сообщение Waiting. Ticket v2/обязательный PlayerCount и новый протокол требуют одновременного обновления клиента, хоста и каталога; protocol4 не допускается. HTTP routes остаются `/v1`; Info.MatchProtocol сообщает5. Форматы существующих StarJournal, MatchJournal и runtime snapshot не менялись.

На каждом соединении допускается один исходящий latency probe. Ответ изменяет измерение только при совпадении nonce; старые/повторные/неожиданные ответы игнорируются. Интервал измеряется монотонными часами в owner thread и включает очереди/планирование обработки, а не только время на линии. Первая проба отправляется при подключении и rejoin, затем периодически. Heartbeat/чаты/RTT не продлевают deadline обязательного batch/hash/turn.

Хост при ожидании более100мс после планового тика публикует номер следующего тика и отсортированные ID блокирующих игроков. Сообщение отправляется при начале ожидания/смене списка, не на каждый проход owner loop. Клиент применяет отчёт только к своему следующему тику; при отсутствии отчёта и новых turns локально показывает ожидание хоста. Duration обновляется локальным монотонным таймером. Продвижение или control transition снимают Waiting.

Waiting и RTT доступны immutable read model и статусу Godot в лобби/бою. При нескольких соединениях краткий UI показывает максимальное последнее измерение, при отсутствии ответа — «RTT —». Диагностика не записывается в журнал, не хешируется и не меняет input delay или скорость игры. Спектатор не становится участником барьера.

## Воспроизводимый native стенд

NET3 verification ждёт ожидаемого spectator до Start. Каждый участник сообщает завершение проверки локального меню, и host запрашивает Pause только после всех подтверждений. Подтверждение паузы также ожидает фиксированный состав стенда. `--slow-client-ms` задерживает только UI-проверку, пока сетевой owner продолжает работать; это воспроизводит прежнюю гонку без зависания симуляции.

Directory verification публикует тестовые лобби на2/8мест и проверяет реальные отключённые кнопки Join/Watch перед входом в поддерживаемое лобби на4места. Финальные native проверки требуют измеренный RTT в статусной строке. Эти fixtures включаются только CLI verification, не обычным запуском.

Пункты1–8 аудита закрываются проверенными сценариями. Восемь прежних ошибок Gameplay baseline, физический WAN/cross-platform, fuzz campaign, NAT/relay backend, производительность больших миров и NET6–NET9 остаются отдельными работами. Текущий сервис не становится доверенным сервером результатов.
